# B 恢复与低输出成本协议设计

2026-10-09。此文件是只读分析与下一阶段设计，未改运行时代码、调用模型、运行优化或仿真，也未回写旧 B 输入、patch、结果或账本。最新用户已明确“记得将调用次数与额度放开”；root 正在负责相应研究范围授权记录。本文不再把旧的 B 次数/token/unknown 准入停止视为新授权的最终状态，但不自行落账、解释成取消超时或求解公平限制。未知用量始终保留为未知。

## 建议先实现什么

建议采用 **完整 v2 输入＋约 65k 的数据页＋完整自身草案的索引表示＋显式差量命令**。初始输入实测为 12 页，每次带全部既有草案的当前 prompt 骨架最大 99,344 bytes。相比把数据页减到 45k 的 18 页，65k 减少重复元数据和旧草案的次数；最终必须检查加入新协议说明、账本、反馈后的真实请求长度。这里的 65k 是表示层参数，不是候选工序数量限制。

先从旧 B 的三个已成功结果恢复**未提交的自身草案**，不要重新调用前三次。B 在新完整观察下逐页明确保留、修改或撤销旧选择，最终再次明确 commit。工具只能进行引用展开、原样编辑和验证，不能为了完成窗口替 B 补排、排序、择机、组批或设置等待。

单纯缩页不能解决问题：45k 会产生更多请求；只保留旧 v1 字段会重新引入信息不对称；无差量协议则每次模型仍会重复输出大量任务。主要可减少的是重复输出、重复观察和失败后重放，不能把未知的推理或网络时间承诺为已降低。

## 快照与当前观察的边界

旧 checkpoint 自带 state hash 验证通过；state 时刻 0、seed 1701、horizon 3600、jobs/executed_tasks/plan_versions 均为空，plan 为 null。故草案从未进入物理执行。

旧 checkpoint 是 `smt-fullfab-env-0.1`，没有当前实现要求的 `implementation_sha256`。当前 `env-0.2.from_snapshot()` 明确拒绝旧版本或缺失实现指纹。**不能改旧快照版本号绕过恢复检查。** 精确重现旧运行只能使用其冻结源版本；那仍是旧观察/旧协议，不能标为当前 A/C 的公平重跑。

推荐新建有父证据引用的恢复运行：在当前获准实现下建立同 seed/数据/初始化的时刻 0 环境，保存当前实现和初始状态哈希，逐字段验证当前观察；只把 B 自身未提交草案作为 lineage 输入。这属于明确记录的新分支，不声称旧快照在新实现下已无损迁移。当前 A/C 的共同初始 problem 可用于开发人员的对称性核查，不能把 A/C 选择、求解结果或指标喂给 B。

逐字段比较完整 JSON（包括原数组位置与类型）结果：

- B 与 A_v4 初始问题：恰有 4,352 个差异，全部为 `/operations/<i>/remaining_work_seconds`。
- B 与 C_v1 初始问题：同样的 4,352 处差异。
- A_v4 与 C_v1 初始问题文件字节相同，SHA-256 为 `f0ed04b301ec8416f0af88749fd8c1efb92061e2371cd9fe0779b2fc346aed15`。
- 913 台机器、4,352 个工序的身份、顺序、其他字段及全部顶层元数据均相同。

冻结旧 observation 计算 `sum(_mean(s.processing_time) for s in route[si:])`，当前从 `route[si+1:]` 求和，排除了当前步骤原始处理时间均值。这不是直接减去导出的 `processing_seconds`：后者可包含装卸等差异。示例 `o0r0l0:1:1` 的 remaining 值从 1,879,363.8 变为 1,852,939.8，差 26,424，而导出 processing 为 26,544。应提供精确旧/新值与定义说明，由 B 判断是否修改，工具不据此重排。

此外，旧 v1 页面未提供原 problem 中的完整条件、资格、历史绑定、虚拟步骤、机器观测标记及顶层冻结/不确定性信息。完整差异清单见 `artifacts/smt_fullfab_semantics/compact-v2-design.md`。修复不能只说“旧任务不变所以无需看新字段”：每一页应有当前完整观察和旧草案，B 明确确认其相关草案；最终确认完整当前 observation hash、所有页 hash 与最终 draft hash。

## 明确选择的紧凑输出与差量协议

已有 709 tasks＋7 holds 的普通紧凑 JSON 为 52,419 bytes。将每个旧 task 无选择地表示为 `[task_id, machine, [operation_source_index...], start, sequence]`，ID 取 `p<原页>t<原数组序号>`，另附字段名与原 holds，实测为 20,561 bytes，减少 60.8%。不带 task ID 的单纯任务行共 13,630 bytes，但不足以稳定增量编辑，故不推荐。数字引用始终绑定**明确的 observation hash**；落盘的规范草案保存原 operation IDs，不能跨新观察盲用旧数字位置。

建议协议版本 `B-explicit-delta-1`：每次响应必须回显 `observation_sha256`、`base_draft_sha256`、所确认页 hash 和 `draft_version`。输入提供当前完整自身草案的可逆索引表示、legacy 来源清单，以及普通验证器逐项返回的事实性错误。新增/删除/修改均只在新恢复目录的 append-only 编辑日志中发生。

支持以下命令；这些是数据操作，不是排程规则：

- `retain`：模型明确确认沿用指定 `base_draft_sha256` 中未被本次命令修改的自身选择。初始载入旧文件只构成未确认草案，不能等同于 retain。允许用全草案 hash 避免重发 709 行，但必须记录已确认的页集合，最终 commit 要求全部当前页得到确认。
- `add`：模型给出新 task ID、明确机器 ID、明确工序 source indexes、start 和 sequence。工具仅按本次 observation 的映射展开原工序身份。
- `patch`：模型指定 task ID 和要替换的字段；未指定字段保留该 task 原值。不能自动补缺失机器、start、batch 成员或排序。批次增删成员必须给出完整的新成员列表。
- `remove`：模型明确给出待删除的 task IDs。工具不因静态评分或冲突自行删除；若引用已执行/冻结任务则拒绝命令并返回事实。
- `reorder`：模型给出某台机器全部可变任务的有序 task ID 列表。必须恰好覆盖该机器待排序任务一次；工具机械赋序号，不能补齐列表、择优保留或移动到其他机器。已执行/冻结前缀不可改。若采用显式 sequence 形式，也必须由模型明确给值，重复值报错。
- `set_hold` / `remove_hold`：模型指定 hold ID、机器、until、`after_task_id` 或明确 immediate、reason；不自动在遗漏机器上加 hold，也不依据队列推算 until。旧 7 个 hold 保留旧“立即等待”的语义，不擅自转为排完任务后等待；B 可明确更改。
- `commit`：回显最终 draft hash、完整 observation/page 版本、valid_until，明确要求执行。不能把最后一次 success、空改动或省略任务解释成 commit。

一个响应可以包含多个明确命令；按模型给出的顺序执行在临时草案上，整批验证成功后原子写入新版本，失败则整批保持原草案并返回所有可判定事实。没有自动修补、fallback 或调用优化器。允许修改已读其他页的自身旧任务；当前只准写本页并 `staged.extend()` 的实现需要改成稳定 task ID 存储与基于明确命令的修改。不能继续以追加造成重复后让工具替模型去重。

模型对页内已有选择全部认可时，仅需 retain、页确认及少量理由；不需重新输出原有任务。任务输出量因此由 **新增＋修改数量** 决定。历史索引草案约 29 bytes/task（含 ID 与少量公共信息的整体均摊）；可用 `约 29×编辑任务数＋命令/holds/理由开销` 作工程字节估计。例如 100 个类似任务行约 2.9k bytes，不是 2.9k tokens。批次长度、时间小数、任务 ID 和理由会改变该数，不能宣称固定上限或真实运行耗时。

45k 每页有 10–358 个可观察工序；这不意味着 B 必须输出同样多任务。组批、明确不选和等待均由 B 自己决定，工具不预设输出数量。保留旧选择不是自动补排：旧草案确为 B 自己的已保存输出，并在完整新观察下再次获得 B 明确确认。

## 中断恢复与后续滚动观察

每次调用前 append 调用意图（request hash、base draft hash、observation/page hash、授权 ID）；结果落盘后 append 响应及编辑事件。一个成功响应用 call_id 和响应 hash 幂等应用一次。恢复只能重新读取并验证已有结果，不重复调用，也不重复应用编辑；最后处于 pending/unknown 的请求不能视为已作选择。需要新调用时使用新 call_id 并保留旧 unknown。

恢复包只包含 B 自身草案与反馈、完整可观察 problem/页、协议、来源 hash。checkpoint 的事件队列、随机状态和其他臂结果不进入模型输入。

窗口内环境已经推进时，先保留已执行与冻结任务，显示全部事实变化。下一阶段可增加 **完整观察的通用结构差量**：按原始键/数组身份列出所有新增、删除、修改，保留未变对象的 hash，并可恢复完整 JSON。不得仅发送“重要”变化、风险打分或候选子集。每次新 observation 重新声明 source-index 映射，旧任务以稳定 operation identity 对齐；无法对应的工序只作为失效事实报告，由 B 明确撤销或替换。物理执行器可以拒绝非法启动，不能据此创建替代任务。

新的 model 编辑日志、原始输入输出和草案哈希必须足以独立重放出执行计划；每项可执行选择应追溯至 B 的 add/patch/reorder/hold/retain/commit，而不是开发工具。没有实测前不声称该协议可以完成整小时或达到 A/C 的质量。

## 可选开发停止点与预算记录

以下是新授权下可选择的开发停止点，不是替用户重新设置已放开的请求数/token配额，也不是已经批准/实施的新调用：

1. **表示与恢复验收**：零模型调用；验证 709 个任务逐项恢复、四份 request fingerprint、完整 v2 往返、幂等编辑和不可改冻结任务。本文已完成其中只读证据核对；新协议单测尚待实现。
2. **小步协议试验**：先完成 1–2 个新的显式 delta 响应，检查能否准确 retain 和修改单项，再决定是否继续。不会伪造已完成全厂计划，也不会将“试验成功”写回旧 failed 结果。
3. **第一份完整全厂计划**：静态 65k 输入需要 12 页确认，另留一次最终全草案检查/commit，算术上约 13 个响应位置；45k 为 18 页＋最终检查，约 19 个位置。可在最后一页同时完成明确 commit 减少一次，但不能自动代为提交。重试、验证错误修订和滚动重排另计，不假装已包含。

180 秒仍是每次上界时，13×180=2,340 秒、19×180=3,420 秒；这只是上界乘法，**不是预测时长**。19 个满时调用单独就超过原 2,700 秒累计模型活动限制，13 个也可能超过既有 B/C 消耗后的剩余活动时间。若该累计限制仍生效，必须按真实账本余量裁剪每次 timeout，并在不足时保留草案停止；调用次数/token准入放开不自动等同于活动时间放开。若需要修改活动时限，应单独记录明确范围，不能由本方案默默延长。
