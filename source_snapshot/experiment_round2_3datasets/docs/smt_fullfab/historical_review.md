## 核实的范围与事实

27 条记录每条均为 8 小时、4 个实际 action 决策事件。输入 manifest 有 913 台生产设备，受控清单仅 `[9,790]`，其余 911 台由旧环境共同背景策略派工。脚本直接按机器组排除 400 个 Delay_32 虚拟资源后计数生产派工，避免用含虚拟等待的派工总数表示生产覆盖。

共读取 108 个 state 文件，得到 216 个“设备×决策状态”观察，其中 135 个候选非空。逐组检查证明：这 135 个观察中，同一设备同一状态的候选预计加工时间仅有一个取值；所有记录候选的 setup_seconds 均为 0。不同设备/时刻之间的工时不必相同。这只对已保存的观察成立，不能扩展成全厂所有状态、所有工步或所有情形都无工时/换型差异。

初始状态在全部 27 条运行中一致：9 号普通设备有 38 个候选 lot，即 38 种立即单 lot 派工；790 号组批设备有 50 个候选 lot，按相同 batch_key 分组、每组从 batch_min 到 batch_max 枚举组合，共 512 种合法立即组批组合。组合数采用 `Σ组 Σk C(组lot数,k)`，不会将不相容 lot 拼在一起，也不会把不足最小批量的组计为立即可执行动作。

场景 801 每条运行最后一次 790 号设备状态有 20 个候选 lot，但只有 1 种合法立即组批组合。其余候选按兼容组拆分后不足最小批量。这个结论仅针对立即派发组合；仍存在显式等待或未来修订等时间维度的决策，不能写成“完全没有任何决策”。

全部 9 组同 scenario×repeat 的 A/C 配对，直接提取 trace 中的 action，比较 action 内容、decision 索引和仿真时刻，序列精确相同（每组 4 个动作）。这不是只比较业务指标相同；也不把 C 的参数或模型文字相同当作实际动作相同。逐配对布尔结果保存在证据 JSON。

## 结论边界

候选多说明有动作选择空间，不能证明这些选择会在 8 小时内对全厂业务指标产生足够差异。旧方案只控制 2/913 台生产设备，未做控制范围代表性、瓶颈影响、预热稳定性、窗口敏感性和可检测效应验证；共同背景派工可以主导整厂结果。

因此旧实验可以作为局部显式派工、真实模型通道、错误处理和事件审计的开发证据。它不能证明三个方案的全厂能力相当，也不能证明求解器增强 Agent 没有价值，更不能用于宣布全厂研究完成。新实验需要验证不同合理合法策略能够产生可重复的全厂业务差异，再冻结正式指标、场景、窗口、预算和样本，不能为了制造差异或令 Agent 获胜而筛选正式结果。
