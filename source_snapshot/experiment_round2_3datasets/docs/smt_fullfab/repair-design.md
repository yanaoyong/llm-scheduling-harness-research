# 全厂计划失效后的修复设计：v4 保留证据，只读研究

建议先开发“提交者明确选择的精确跳步取消”，并保留有预算的全量重解；局部经典修复作为第二条对照。v4 的30次失效都由一个已确认跳过的单lot任务触发，传播范围远小于全厂，但本分析没有执行取消、修复、CP或仿真，不能据此声称节省了实际成本或改善了产出。

本文件不修改运行接口，也不批准后续预算。当前执行规则仍是全部pending一旦发现route/visit失效就请求重排。历史v4没有提交取消授权，不能回头把其任务视为已授权取消，原failed结果保持不变。

## 输入与计算口径

输入为冻结提交 `0004984dc1739c5057fa5cd7f9ab70940170315a` 的 `runs/smt_fullfab_development/A_1701_1h_incumbent_v4/`：`trace.jsonl`、30个 `problem_00000..00029.json` 和30个 `solver_00000..00029.json`。未调用求解器、环境推进或模型，只用Python标准库读取JSON、构图和计数。

61个输入的摘要计算方式为：先trace，再按文件名排序的problem，再按文件名排序的solver；逐文件追加UTF-8的 `文件名:文件SHA256\n` 后整体SHA256。结果为 `e629fb5b692e2db70d5f60b2adf35adb302836067ec32758fe0a8bdad58a52ea`。独立前缀审计、成本记录与限制另见 [A-development.md](A-development.md) 和 `artifacts/smt_fullfab_optimizer/A_1701_1h_incumbent_v4-{analysis,prefix-audit,cost-and-replans}.json`。

计数按每次失效时的状态截面，重复出现的任务、机器和工步会重复计数，不是独立lot总数：

1. 顺序读取trace，用ready/skip/dispatch事件重建当前工步及visit，用lot_complete标记完成；以 `(plan_version, task_id)` 的生产dispatch记录排除已启动任务。没有假设未来抽检结果。
2. **已提交剩余集合 P**：当版 `plan_committed.plan.tasks` 中尚未启动的任务，已经按3600秒观察终点裁剪。**完整预测剩余集合 F**：同版solver的四小时plan中尚未启动的任务。两个分母分别报告。
3. **直接根 R**：P中任一成员已完成lot、当前工步已越过声明step，或观测visit已超过声明visit的准确任务，判据与冻结环境一致。逐个确认根任务的精确 `(lot,step,visit)` 在trace中有skip证据，不把尚未到达任务当作失效。
4. **工艺闭包**：从R沿完整预测任务的 `predecessor_task_ids` 向后遍历，包含根。再用保存problem的operation前驱图映射到task校验，没有发现缺失边。
5. **工艺与机序传播包络**：在上述图加入每台机器按sequence相邻任务的有向边，再求后继闭包。这包含移除任务可能改变的机台后缀状态和跨族后继，不意味着所有这些任务必须重排，也不是局部修复可行性证书。
6. 另对F重新扫描全部失效根，避免只修日志首先报告的一项。若准许重选机台/组批，进一步将包络涉及的设备族扩大到该族全部公开工步和全部资格机器；未排工步也进入候选域，不能只保留已选中的lot。

这个显式图不覆盖重新组批、资格替代机器上的竞争、计件PM、当前承诺之外的新任务和未来随机变化。实际修复仍须验证setup/minrun、已知down/占槽、绑定、冻结承诺、工艺先后及批下限；边界不成立时必须扩大范围或失败退出。

## 三种策略比较

|方案|明确改变什么|必须保留与检查什么|成本与公平边界|
|---|---|---|---|
|FULL：全量经典重解|对当前完整problem重新生成全厂计划|已开始任务和冻结承诺；全部lot仍进公开候选；新完整计划再次审计|现有A/C共享工具；B不得调用。是正确性控制组，成本最高的可能性需实测，不能预设必然最差|
|LOCAL：局部经典修复|重新规划声明修复域内的任务/批/选机/时间；输出完整新版本及精确diff|修复域外计划不可被悄悄改变；边界加工占槽、setup/minrun和前驱到达必须显式锁定；所有新生产仍来自新计划|A/C同一接口和预算；属于优化工具，B禁止使用。域扩张和验证开销计入总墙钟；不能声称只处理图中1–9台机器就充分|
|COND：提交者预声明的条件取消|仅在精确已观测skip成立时，移除指定的、已不可能按原成员执行的完整任务|其余lot成员、设备、机上相对顺序、not_before和声明窗口逐字段不变；不得重组选lot、缩批、插入新任务、默认派工或自动提前启动|可以作为共同计划语言，A须预登记，B/C须在提交计划时明确选择并声明。执行器只机械兑现已提交条件，不调用优化/补齐|

FULL仍是局部方法失败后的可选处理，但必须提前写入对应控制器策略并消耗同一累计预算。B不能通过“失败后兜底”间接获得FULL/LOCAL；B需返回模型修订或按已提交等待/失败规则停止。

LOCAL最初可采用固定批、固定机器的后缀时刻修复，证明边界安全后，再开发设备族内重优化。固定批修复不能称作与全量同强度的优化；族内重优化也必须让同族所有可见lot参与资格检查，并维护周期性全厂刷新，不能把原来未排的lot永久排除。新候选对外部前驱/机台的需求若超出已锁定边界，应扩域并重新计预算，超过上限则返回可审计失败。禁止仅为控制成本把困难需求变成长时间hold。

## COND 的最小语义与反例

下面是设计约束，不是当前接口字段已实现的声明。与接口v2整合前须单独冻结schema和审计版本。

- 授权绑定 `plan_version + task_id + 完整lot/step/visit元组 + 机器 + 机序`，并记录提交者、原始方案hash。仅源输入 `conditional=true` 不构成取消授权；B/C原始输出必须明确选择该分支，不能由解码器默认添加。
- 首阶段仅支持“此精确工步访问已被共同物理环境记录为skip”。一般route变化、未来可能skip、CQT冲突、模型估计加工不划算均不满足触发。返工visit变化先保留请求修订，避免误把需要重做的lot永久删掉。
- 单个批成员被skip时，原准确批任务已不可能按原成员执行；若提交者提前声明，可取消整个任务，不能自动缩批或找lot补齐。其余仍需要该工步的批成员显式列为未排并交回原提交者处理。本v4没有多lot根，不能用这30例声称多lot分支安全。
- 对剩余任务做稳定删除：只去掉获授权的准确任务，其余相对机序和开始条件保持不变。允许序号有空洞，不能因取消而把后继前移、重新计算一个更早的not_before或改变机台。
- 若后继声明了“必须该任务完成”，不能将取消伪装为完成。只有计划提前定义了对应精确lot工步的“实际完成或实际skip已被观察”的前驱分支，才可机械判定该条件。未声明分支的悬空依赖必须失败请求修订；不能递归删除仍可能执行的后继。
- `after_task_id`尾部hold目前只在任务已dispatch时生效。取消后不能自动创建无限hold或把未提交hold改为生效。提交者需提前声明“该准确任务被合法取消后，仍按所提交截止时刻等待”的等价分支，否则报告责任覆盖缺口并请求修订。
- 删除一个任务可能改变后缀setup/minrun计数。共同执行器仍验证实际开始合法性；条件取消不授予改写后缀setup/end或替代批量的权力。独立验证无法确认保留序列可执行时应请求修订。所有生产开始继续要求显式方案归属。
- 审计需记录原授权hash、准确skip事件seq、取消前后计划hash及差异，验证被移除任务尚未启动、没有额外成员变化、没有重排/插入，并继续检查机会覆盖与未排等待。重复skip通知必须幂等，未授权取消必须拒绝。

这让B拥有与A/C相同的条件表达能力，但不会替B选择取消列表、生成设备顺序、调用求解器或修复缺失字段。C只有真实选择并提交该策略时才获得对应执行语义，工具调用、返回方案及最终被采用版本都必须留证。A/C共享LOCAL/FULL函数、候选生成、验证器和统一预算账本；不得维护一个私有更强的C修复器。

## 理论可避免的重算量，不是实测节省

v4实际共30次付费求解：1次初始计划，前29次失效之后各有1次重解；第30次失效后因预算耗尽而没有第31次求解。因此与已发生失效相关的**历史付费重解池**上界是29次、58秒预约、5044次族/层调用、54.731321秒实际CP、281.569942秒计划器墙钟。不能把第30次未发生的求解也计为已经节省的成本。

如果在固定的这些截面上，所有条件取消都能独立验证成功且无需其它修订，则这29次是“理论可能避免”的总调用池。真实净节省未知：取消后计划和后续物理事件会分叉；仍需条件检查、日志、验证和周期刷新；部分取消将失败，局部修复也可能扩大到全厂。不能从0.5609%任务包络直接推导99.44%的CPU节省。

同理，6568个P任务截面中有6519个在机序包络之外，61689个F任务截面中有61343个在全根包络之外，可视为优先尝试保留的结构规模；它们不是已被证明可原样执行的安全任务。族域6815工步也只是第一层扩域规模，不能当成经过全约束证明的局部模型大小。

若后续采用绝对仿真时刻每1800秒全厂刷新，在2672.85秒前缀内至少还有一次1800秒刷新应发生。当前v4的相对周期会被每次修订重置，不能把全部29次去掉又假设不存在刷新成本。采用绝对周期是一项需共同冻结的实验变更，必须重跑同版FULL控制组；旧v4仅作设计证据，不能直接充当新接口性能对照。

本提案不新增B/C真实调用。未来B/C比较前，先冻结同一条件语言和独立审计；B只能由模型原始提交选择条件、列表和顺序，C可真实调用同一A/C工具，任何预算、模型调用与token上限须另行前置登记。当前工作仅交付本只读设计文件。

## 后续获准的最小实现：周期CP加事件全厂经典构造

上述量化与三策略比较保持为设计证据。主流程随后选择先实现 `src/smt_fullfab/hybrid.py`，当前没有实施COND，也没有改共同执行器、B/C控制器、观察接口、物理规则或独立审计。新增模式通过 `runner --solver-method hybrid` 选择，旧运行及其失败结果均保留。

周期点0、1800、3600……采用已有全厂 `solve_decomposed_plan`，事件点采用已有全厂 `build_incumbent`。后一函数从当时公开的完整problem重新构造未来多步计划，涉及跨族工序先后、组批、资格选机、setup/minrun、已知停机/占槽、未来同机绑定、明确机序与开始条件；它不是背景即时派工。所有选中任务仍由方案明确提交到同一个执行器，未排工步和构造预算截断原因继续留证。

具体接口为 `solve_hybrid_plan(problem, mode, config, time_limit_seconds, seed, weights, plan_version)`；`configuration(...)`冻结构造规则和上限，`HybridSchedule`负责可序列化的绝对周期。未来C只有显式选择此工具、承担其成本并应用返回方案后，才使用该路径；当前C已保存的运行不会因新代码自动改变。B没有工具接入或自动补齐。

- **周期不漂移**：`next_full_at`只在周期方案经执行器成功commit后移动到下一个绝对1800秒网格点。事件构造不移动截止；`advance_plan`最多推进到该截止。仅预约、求解成功但commit失败，都不能移动周期钟。
- **预算不暗中续期**：周期必需优化缺少剩余CP预算时直接失败，不隐式改为事件构造。事件构造明确预约0 CP秒，但记录构造秒数上限、候选评估上限、实际构造墙钟及总计划器墙钟，不称其免费或最优。构造上限是已有构造器循环的停止边界；输入归一化、候选生成和最终独立校验等使整个调用可能超过该秒数，故仍受runner及外部墙钟边界约束。
- **不隐藏错误**：名义检查失败返回失败状态并保留候选/错误，不切换另一个算法。有需求却没有任何任务也返回NO_PLAN。周期优化仍使用其原先已公开的“经典候选加CP改进”内部流程，原CP状态和候选来源保留，没有新增失败后的隐式兜底。
- **槽位公开**：周期分解维持每机每层4个slot；事件全局构造按 `4 × lookahead_depth2 = 8` 个总slot。二者策略和候选池并非完全等价，因此不声称这一换算证明质量相同，也没有按机器列表永久删掉lot。
- **恢复必须一致**：checkpoint保存hybrid schema、固定配置、上次commit时间、上次周期commit时间、下次绝对截止。恢复核对period、plan窗口、depth、slot、周期CP请求、构造秒数和候选评估上限；旧checkpoint缺少状态时拒绝推猜。CP累计请求、构造实耗、计划器尝试数、runner墙钟和历史run日志字节均继承。已登记的CP总额、max_plans、wall_seconds、max_log_bytes不能在同一恢复链内提高或清零。

runner结果新增 `planner_calls`、`classical_event_calls`、`actual_cp_solve_seconds`、`planner_wall_seconds`、`classical_construction_wall_seconds`及累计资源字段。`solver_calls`在hybrid中统计正CP预算预约的计划器调用数，不是底层族/层CP搜索次数；底层记录仍在各solver响应中。构造墙钟包括该构造器自身的独立名义校验，周期分支将各共享incumbent的相同口径相加。异常缺少细分耗时时填null，并保留已知整体墙钟与预约，不把缺失值计为0。

资源账本仍使用 `solver_reserve/solver_finish` 事件以兼容现有读取，但每条新增明确 `planner_mode`。`event_classical`的0 CP预约不代表0成本，必须连同构造实耗、全部计划器尝试和整个run墙钟阅读。新的hybrid恢复按尝试数执行max_plans，失败尝试也不退款；墙钟及日志阈值仍是操作边界检查，最后一批可能越界。
