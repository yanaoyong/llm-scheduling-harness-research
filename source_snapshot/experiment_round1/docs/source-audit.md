## PADL 编码的精确语义

以下行号相对 `vendor/FJSP-SMT2020/PADL-2023/encoding_msw.lp`。

1. **工序与机台**：7–20 行由 wip/product 生成剩余工序；36 行在 `flex=1` 时恰好选择一台所属组的可用机台。机台集合由 `machine_selection.lp:10–22` 给出：每组使用 `1..min(实例机台数,剩余工序数)`，公开实例编号连续。
2. **工艺前置**：58–61、230 行要求同批的 `S+1` 至少晚于 S 的加工完成。无抢占，工时直接取 product 的 Pro_t；不是再乘晶圆数。
3. **机台互斥**：45–55 行为不同批同机工序选择先后，230 行施加加工时长间隔。同批由工艺顺序决定。所有原始正式实例同组都有两种 PM，64–87 行补全同批同机次序和相邻判断。
4. **维护分段**：114–115 行由求解器决定在哪道工序前执行何种维护。136–137 行要求机台首工序附上该组全部维护类型。139–159 行要求每段（一次该类型维护后到下次之前）累计工作量不超过 Max；若之后还有同类型维护，这个已闭合段还必须不少于 Min。最终未闭合段免 Min。`counter_based` 按晶圆数累计，`time_based` 按工序纯加工时间累计；等待、换型和维护自身时间不参与 time-based 累计。
5. **维护耗时**：162–170、195–206、232–233 行将不同维护类型的时长相加，并与换型时长相加，插在前一机台工序完成与当前工序开始之间。源编码可能产生若干部分和 duration 原子；最大和约束起作用，转换排程不应把这些重复相加。
6. **首台维护的边界**：首工序强制附维护，但其时长没有第一道工序的下界。源码只对存在前机台工序的边增加维护时长，因此可解释为初始已维护状态。本轮必须保持这点，不能一边让原代码忽略首维护，另一边让 B/C 支付首维护时长。展示时应标为初始状态，不绘成负时间或占用型维护。
7. **换型继承**：117–127、173–193 行规定初始非零 setup 或同机有效 setup 变化时需换型。需求为 0 的工序继承最近非零 setup，而不是强制恢复 0。换型时间查 `setup_change(G,name,duration,min_runs)`；product 的 Setup_t 字段没有用于排程时长。
8. **首换型与释放**：217–225 行：批次当前首工序有换型时 `start>=R+setup_duration`，否则 `start>=R`。227–228 行：机台首工序若还有后续机台工序且有换型，则 `start>=setup_duration`。若机台仅有一个工序、且它不是批次当前首工序，源代码没有该额外首换型下界，校验器应保留这一边界。
9. **机器时间边**：232–233 行要求机器前驱完成后才支付当前换型/维护总时间。批次工艺前驱仅约束生产加工开始，不要求等前道产品完成后才开始准备当前机台。
10. **makespan**：235–237 行取所有批次最后一道工序完成时刻的最大值。
11. **setup 最少连续使用次数**：212–214 行是软约束，每个非最终换型段中工序数量小于 Min_r 时罚 1。末段免罚。它不是硬可行性条件；若低于最低次数的短段不被判可行，就擅自改变了原问题。
12. **未建模字段**：due_time、priority、pro_unit、cascading_interval、load/unload 没有变成额外时间窗、延期目标或上下料时间。本轮不宣称覆盖这些现实约束。

## 未泛化的源码边界

- `lot_release(L,R)` / `num_wafer(L,W)` 用 L 投影（17–18 行），`pro(P,S,T)` 用 P/S 投影（21 行）。不同产品复用 L 且 release/W 不一致时会造成歧义；当前公开实例值一致，安全。解析器应拒绝这种冲突，不能默默挑一条。
- 无 PM 的组中，同批再次访问同机时的 `pair`/`tool_order` 在 64–68 行缺失，可能影响换型。当前原实例各组都有 PM，因此不受影响；人工冒烟也必须有 PM 或明确只测该未覆盖边界，不能把本校验器宣称泛化至任意扩展输入。
- product 步号若不连续，58–61 行只连接 S/S+1，无法自行填补工艺空洞。本轮原始实例连续。
- README 的文件表把 `encoding_msw.lp` 写成 `encoding_mws.lp`（18–20 行）；Usage 命令拼写正确。

## 求解器编译、目标控制和状态解读

- 原文推荐 `clingo-dl encoding_msw.lp instance --minimize-variable=makespan --const flex=1`（PADL README:34–40）。
- 实测 `python -m clingodl --help=2` 缺少 `--minimize-variable`。官方 Python 入口 `libpyclingo-dl/clingodl/__main__.py` 自述 excluding optimization；只装 pip 包不能假定完整复现上述命令。
- 已克隆官方 <https://github.com/potassco/clingo-dl> 的 v1.5.0，固定提交 `4f91f6233b441864ccc39195b6b7b515d92bd848`。使用未修改的 `app/src/main.cc` 和 `app/lib/src/app.cc`，clang++ C++17 编译，链接已锁定 pip 的 clingo 5.8.2 / clingo-dl 1.5.0.post1 提供的动态库。`src/build_solver.py` 保留可复现命令、工作目录和版本输出于 `vendor/clingo-dl/build/build.json`。上游 clingo-dl 源码为 MIT 许可证。
- 本轮 A 是原 PADL 编码加原生官方优化器的运行复现，不是 CP-SAT 语义重新实现，也不是 FIFO。
- 官方 `app/lib/src/app.cc:72–88,109–129,151–167` 的 Optimizer 每找到一个模型便结束当前 solve，加入 makespan 小于当前值的界，再次求解。`--minimize-factor` 默认 1。本轮主目标是 makespan，setup 软约束完整保留并单独记录。这个控制器不在最小 makespan 上继续完成 setup 二级优化；不能声称证明了 `(makespan,setup违例)` 字典序最优。
- 为验证弱约束不会留下一个妨碍更小 makespan 的旧成本界，另做可手算双选项微测：强制先选 `(x=2,soft=0)`，随后原生优化器成功找到 `(x=1,soft=1)`，再证明 `x<1` UNSAT。这验证每次 solve 的 soft 优化界重置。另一微测让两候选都有 `x=1`，强制先找 `soft=1`，优化器即结束，未找同 x 的 `soft=0`。原始输入、命令和输出均在 `runs/development_objective_probe.json`，不属于正式评测。
- 原生 CLI 最终 JSON 的 `Result=UNSATISFIABLE` 和退出码 20 可能表示最后一个严格更优界不可满足，而不是原问题无解。必须保留前面 `Call[].Witnesses[]` 的最后一个有效完整模型：若有模型且最终界被证伪，可标为 makespan 已证最优；若时间限制返回且有模型，只标可行/限时 incumbent。没有 witness 才能判断原问题 UNSAT。
- `src/show.lp` 只增加输出投影，不加约束或更改优化权重。`src/classical.py` 按真实 `mach_assign/6`、`assign/3`、`dl/2` 原子转换排程；实际可行性仍由独立 validator 判断。

开发运行：只运行公开开发实例 01，原生求解器输出 8 个逐步改进 witness，最终 makespan 120，setup 罚值 2；求解器内部 Total 约 0.017 秒。完整首次运行原始 JSON 留在 `runs/dev_native01.json`。集成运行和独立校验记录见 `runs/dev_classical01/`。开发记录与正式记录分开，正式结果不由此预填。

## 比较口径补充

A 在结果出现前固定为 `frumpy` 预设，三次种子为 11、22、33；C 可以在相同累计40秒限额内选择其他预设和种子。因此相对A的收益是相对这个固定参数经典基线的收益，不是已经击败经过充分调优的全部经典求解器，也不能将预设本身的差异归因于LLM。下一轮需要固定参数/固定预设组合的消融。

`end_to_end_seconds` 的实际计时范围从实例解析及初始输入快照落盘之后，到模型/求解/排程与独立检查完成、生成结果字段时为止；包含该执行阶段的工具与日志开销，不含Python启动、初始解析和最终result文件写盘。`solver_first_witness_seconds` 是求解器内部首次模型时间，单独记录。模型通道时间含CLI与网络，纯服务端推理时间未知。正式评测为本机单进程串行，不宣称隔离了桌面环境的所有背景负载。
