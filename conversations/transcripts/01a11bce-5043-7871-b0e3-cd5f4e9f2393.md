## assistant · 2026-10-09T00:52:55.897Z · 原记录 L979

**Makespan 指一批任务全部完成所需要的总历时**，通常记作 \(C_{\max}\)。

在本轮实验中，从统一的时间零点开始，取所有工序中最晚的完成时刻：

\[
C_{\max}=\max_i C_i
\]

例如，两台设备并行生产，设备 1 上最后一个任务在时刻 80 完成，设备 2 在时刻 100 完成，那么 **makespan 就是 100**，不是两者相加的 180。

**为什么越小越好？** 因为三种方案面对相同的任务和设备、遵守相同约束，makespan 越小，意味着这批任务能越早全部完工。优化顺序、设备分配、换型和维护安排，可以减少等待，使最后的完工时刻提前。

拿我们实例 05 的第一次运行来说：

| 方案 | Makespan |
|---|---:|
| A 经典方案 | 174 |
| B 直接 Agent | 202 |
| C 求解器增强 Agent | 156 |

C 比 A 提前 **18 个题目时间单位**完成全部任务。这里沿用数据集的时间单位，没有将它假定为分钟或小时。

还要区分两个时间：**makespan 是排程方案对应的生产历时；报告中的“运行耗时多少秒”是电脑生成这个方案所花的时间。** 一个方案可能算得慢，但安排出来的生产过程更短。

“越小越好”针对本轮的优化目标成立。实际工厂还可能更关注交期违约、重点订单、在制品数量等，单独优化 makespan 不代表所有业务指标都会更好。

**A 的实现：把问题交给原作者的数学约束模型，由求解器搜索。**

我们采用作者的 **PADL-2023 原始 ASP 编码，加上 clingo-dl 求解器**。ASP 可以理解为用逻辑规则描述离散选择，再用差分约束处理时间关系。

输入首先明确：

- 每个批次有哪些剩余工序、工序之间的前后关系；
- 每道工序可以使用哪个设备组；
- 每组有哪些设备；
- 加工时间、换型时间；
- 各类维护的累计负载上下限及维护时长。

求解器需要联合决定设备分配、同机顺序和维护位置。选择一旦确定，就必须满足对应的时间约束。例如，同一台机器连续执行两道工序时，后一工序不能早于：

\[
前一工序完成时间＋必要换型时间＋本次维护时间
\]

这些选择不是彼此独立的：换一台设备可能减少等待，却引入换型；调整顺序可能减少换型，却触发维护或延迟下游工序。求解器通过约束传播和搜索处理这些组合关系。

原优化控制器的工作过程是：

1. 找到一份满足约束的排程。
2. 假设其 makespan 为 \(M\)，继续要求寻找 makespan 不超过 \(M-1\) 的方案。
3. 找到更好的方案后继续收紧。
4. 直到证明不存在更好的方案，或者达到时间上限。

因此，**固定参数不代表只算一次、也不代表不会改善排程**。一次求解调用内部可能已经产生了很多个逐步改进的候选。

第一版的具体配置是：

| 参数 | 设置 |
|---|---|
| 机台分配 | `flex=1`，允许组内自由选择 |
| 主目标 | 最小化 makespan |
| 搜索预设 | `frumpy` |
| 每次求解上限 | 40 秒 |
| 三次重复的随机种子 | 11、22、33，事先锁定 |
| 大模型调用 | 0 |

`frumpy` 是求解器的一组搜索配置预设，不是一个排程规则。不同预设会影响搜索过程，因此在相同时间内找到的解可能差很多。

**这也是 A 当前结果的局限：我们测的是“原模型＋固定 frumpy 配置＋40 秒预算”，没有先做充分的参数调优。** 它不能代表所有经典求解方法的最高水平。

**B 的实现：大模型给出完整的排程决策，程序负责把决策转换成时间表。**

B 使用真实的 `gpt-6-astra` 模型，推理配置为 `medium`。

每次请求交给模型的内容包括完整实例、约束说明，以及这条运行已有的错误反馈。模型需要输出一份**有顺序的完整动作列表**，每条动作包含：

- 要安排哪道工序；
- 分配到其设备组中的哪台设备；
- 在这道工序之前安排哪些维护事件。

动作列表既确定工序的派工顺序，也确定各台机器上的执行顺序。它必须遵守批次前后序：前一道工序先出现在列表中，后一道工序才能被安排。

这里有个重要细节：**当前 B 不是每安排一道工序就调用一次模型。它一次模型请求输出整份方案。** 15 道或 30 道工序，都放在一份动作列表里。

随后，`dispatch.py` 按模型指定的顺序逐条执行。它维护这些状态：

- 每个批次前一道工序何时完成；
- 每台机器最后一项任务何时完成；
- 机器当前的 setup；
- 每类维护已经累计了多少加工负载。

对一个普通的非首机工序，时间计算主要是：

\[
开始时间=\max
\left(
批次前序完成时间,\;
同机前序完成时间＋换型＋维护,\;
适用的释放时间下界
\right)
\]

例如，批次前序在 60 完成，所选机器在 40 空闲，换型和维护共需 13，那么这道工序最早在 `max(60, 53)=60` 开始。首机工序则按原版本的初始状态规则单独处理。

**这个程序不替模型选机器、不交换工序顺序，也不自动补维护。** 模型决定错了，程序就返回错误。例如：

- 前序工序还没有安排；
- 维护做得太早，未达到最低使用量；
- 累计负载超过维护上限；
- 漏掉了某道工序。

模型收到反馈后，可以重新输出完整动作列表；每条运行最多四次模型请求。但当前停止规则是：**一旦完整排程通过校验，就立即接受，不再要求模型继续改善 makespan。**

因此，B 当前有两项明显特点：

- 模型必须直接承担排程质量，工具不会帮它搜索更好的组合。
- 可行性修复有接口，但“可行以后继续优化质量”的循环尚未加入。

正式实验中，B 的九次运行都第一轮可行，所以每次只调用一次模型。它在实例 05 排出 202、203 的方案后也会停止，因为这些方案虽然质量较差，但没有违反硬约束。

从你熟悉的 C++ 排程角度看，**B 相当于模型生成机器序列和维护决策，确定性解码器根据这些决策计算时间表**。模型内部究竟采用了什么搜索思路，我们不能从输出完全确定；能够审计的是它实际给出的决策和反馈。

实现见 [dispatch.py](__LOCAL_PROJECT_ROOT__/experiment_round1/src/dispatch.py)，模型收到的任务说明见 [B 提示词](__LOCAL_PROJECT_ROOT__/experiment_round1/configs/prompt_B.txt)。

5. 正式版本冻结后不原地修改。后续修复使用新提交、新实验版本，保留旧结果和失败记录。

6. Git 跟踪代码、配置、提示词、测试、协议、精简结果、报告和进度。虚拟环境、缓存、构建产物、凭据、大型原始数据和超大日志不得直接塞入 Git。

7. 对未进入 Git 的数据与日志，提供清单、校验和、获取或恢复方法；实际文件仍保存在本实验目录中。不能因为 .gitignore 而丢失审计证据。

8. 禁止提交令牌、登录文件、带密钥的环境配置。不要使用破坏性的 reset、clean、强制推送或历史改写来整理进度。

9. 维护 progress/STATUS.json 和追加式迭代记录，写清当前阶段、最新有效提交、已完成运行、失败、阻碍以及下一条恢复命令。

10. 并行开发遵守第十一节的文件归属、分支和集成规则。Git 提交与冻结标签默认由主 Agent 统一组织。

三、三类数据承担不同的实验任务

1. Brandimarte：校准排程质量。

   核查原始来源、实例版本、公开最优值和上下界。用明确的参考结果判断三种方案距离最优或最好已知水平有多远。

2. Hurink：分析设备柔性的影响。

   对同一个基础实例，比较 edata、rdata、vdata 等版本，观察设备选择集合变化后，质量、可行率、稳定性和成本如何变化。

   不把 Brandimarte 与 Hurink 的整体差异直接归因为设备柔性。

   开发集和正式集必须按基础实例分组划分，不能把同一基础实例的不同变体分别放入开发集和未见验收集。

   每个变体对照自身的最优值或上下界，不能跨变体套用参考答案。

3. SMT2020：验证半导体场景适应性。

   使用完整官方工厂数据及明确版本的仿真实现，优先核查 Dataset 2 的 LV/HM 场景。

   不得把首轮几十道工序的 PADL 实例或自行抽出的普通 FJSP 子问题称为完整 SMT2020 实验。

   明确它是公开仿真测试床，不能宣称是某家工厂的真实生产流水记录。

优先核查以下来源，并追溯原论文及版本：
- https://github.com/SchedulingLab/fjsp-instances
- https://scheduleopt.github.io/benchmarks/fjsplib/
- https://p2schedgen.fernuni-hagen.de/downloads/simulation
- https://zenodo.org/records/15088815
- https://github.com/david-dd/PySCFabSim-revised

这些是核查入口，不代表已经批准其中任意版本或确认实现完全正确。记录下载日期、提交或版本、文件哈希、许可证和约束语义。

对参考答案逐项标注：
- 已核实的最优值；
- 文献或维护表报告的最优值，证明尚未独立复核；
- 最好已知可行值 BKS；
- 下界；
- 未知。

不能把 BKS 当成最优值。不能给原实例增加约束后继续引用原最优值。运行时不得向 B/C 暴露参考排程、最优值、其他方案结果或相关检索入口。

四、三种方案的实现边界

A：经典排程方案

- 使用有明确来源的经典求解方法，优先可复现的参考实现；必要时语义等价重实现，并明确标注。
- 可以在开发集上调试参数，然后冻结；不得故意使用弱参数制造 Agent 优势。
- 静态 FJSP 可使用成熟 CP、CP-SAT 或其他适合的经典求解实现。
- SMT2020 可采用固定策略的滚动优化；FIFO、CR 等原始派工规则另作为参考，不得悄悄替代主要经典优化基线。
- 记录算法、模型、参数、种子、预算、可行解、界及最优性状态。
- 固定参数不等于固定输出，求解器仍须根据每个输入实际求解。

B：直接排程 Agent

- 必须真实调用大模型。
- 由模型决定受控范围内的工序顺序、设备分配，以及该问题包含的组批、等待或重新安排等核心决策。
- 工具可以查询状态、计算时间、执行动作、检查约束和反馈错误。
- 工具不得通过求解器、固定启发式、参考答案或预计算计划替模型完成核心决策。
- 时间计算或排程解码器的权限与语义必须明确；若它限制了可表达的排程，须报告该限制。
- 允许批量动作和反馈修订，但不能用 mock、写死输出或人工代排冒充真实 Agent。

C：求解器增强 Agent

- 必须真实调用大模型。
- 由模型选择求解动作、参数、时间分配、滚动窗口或局部修复条件，再检查结果，必要时调整。
- 尽量与 A 共用同一约束模型和求解工具，以便识别 Agent 的实际作用。
- 保留每次模型决策、工具参数、求解反馈及最终选择。
- 如果只是一次默认求解器调用，必须如实报告。
- 添加必要的固定参数或固定策略组合对照，检验优势是否仅来自换了参数。该辅助对照单独统计，不冒充第四个主要方案。

B/C 尽量使用相同模型、推理配置和同等级状态信息。不同方案的文件、会话、候选解和中间结果须隔离。

五、先建立协议，再扩大运行

对每类数据先做最小贯通：

真实输入 → 决策或求解 → 排程/动作输出 → 独立检查 → 结果记录 → 可视化。

先设置手工可核对的冒烟实例和开发集。完成探测后，在批量运行前写入：
- 问题规范和约束；
- 输入输出及动作格式；
- 开发、正式和预留实例清单；
- 模型、提示词、工具和参数；
- 资源、步骤、重试及超时上限；
- 评价指标、失败分类、停止条件；
- 恢复机制和正式验收规则。

目标核心正式矩阵：

1. Brandimarte：
   至少 3 个按规模、结构或难度预选的实例，A/B/C 各运行 3 次，共至少 27 条。

2. Hurink：
   至少 3 个未用于开发的基础实例，每个包含 edata、rdata、vdata，A/B/C 各运行 3 次，共至少 81 条。

3. SMT2020：
   至少 3 个预先锁定、未参与调参的外生场景或随机种子，A/B/C 在每个场景各运行 3 次，共至少 27 条仿真记录。

核心目标至少 135 条记录，辅助对照另外统计。

先实测成本再制定可承担的正式计划；预算不足时保留未完成格点，不能无限运行或降低标准后宣告完成。

正式实例不能根据某种方案容易成功而事后挑选。查看正式结果后继续调参，必须标为开发迭代，并使用新的预留验收集和版本。

六、SMT2020 的专项要求

1. 独立核查仿真器与数据的对应关系，建立约束覆盖表：组批、换型、维护、故障、运输、重入、设备绑定、抽检、返工等，以所选版本实际定义为准。

2. 区分生产设备和虚拟运输/等待资源。不得直接把设备表所有数量相加当成生产设备数。

3. 正式协议固定初始 WIP、投料、仿真窗口、预热方式、受控设备组、动作频率和外生随机过程。

4. 本轮先以“完整工厂环境中的明确受控范围”实现可承担的滚动实验。受控范围应涵盖组批及非组批决策；范围外使用三方案完全相同的固定环境策略。

5. 必须预先列出 Agent 控制了哪些设备、哪些决策，以及控制占比。局部控制成功不能称为全厂自主排程成功；静态快照成功不能代替动态闭环成功。

6. B 在受控范围内仍须由模型决定实际动作，不得只选一个派工规则后让规则包办所有决策。

7. 模型只看到当前可观测信息，不得提前看到未来故障、返工抽样或其他方案结果。

8. 使用可比较的外生随机场景。仅设置相同全局种子不一定保证公平，应检查策略改变调用顺序后是否改变随机事件；必要时采用事件键控或独立随机流。

9. 明确处理终止窗口中尚未完成的批次，报告积压和初末 WIP，防止只统计完成任务造成幸存者偏差。

10. 不要求仿真窗口内所有新投批次完成全工艺，但必须完成整个预定窗口、所有受控决策、事件记录和独立审计。超时、提前退出、自动接管均如实计入。

11. 仿真系统随机性与模型随机性分开记录和分析，同一个场景的重复运行不能全部当作独立工厂场景。

七、独立校验和指标

为静态 FJSP 建立独立校验器，检查：

工序完整性、唯一设备分配、设备资格、设备相关工时、工艺顺序、资源容量、时间范围及所有所选版本的硬约束，独立重算 makespan。

为 SMT2020 建立动作和事件轨迹审计，检查：

批次流转与守恒、合法设备、组批兼容及容量、时间与加工语义、换型、维护、故障处理和其余实际生效的硬约束。

不能仅复用模拟器的 success 标志证明自身正确。

使用手算小例和故意违规的排程/轨迹验证检查器。必要时与参考实现交叉验证。

FJSP 至少报告：
- 可行率、首次有效输出率和修订后成功率；
- makespan；
- 相对已知最优值、BKS、下界及配对 A 的差距，分别命名；
- 耗时、模型调用量、修订次数及成本。

SMT2020 至少报告：
- 完成仿真与合法决策情况；
- 吞吐量、生产周期、延期及在制品变化；
- 批次填充情况、设备利用与瓶颈表现；
- 决策延迟、重排次数、模型和求解成本。

根据所选场景预先固定主目标与其他指标的约束，不能看完结果再换权重。不同数据集、不同目标分别比较，不把它们的原始目标值相加或混成一个总冠军排名。

失败目标值不能记为 0，也不能从成功率统计中删除。质量均值须说明是条件于成功的统计，并同时展示失败。

八、真实模型与资源控制

1. 优先复用首轮已经验证过的真实模型通道，先做最小真实调用；当前路径和登录是否有效须重新核实。

2. 不把交互登录直接假定为 API 凭据，不读取或输出敏感令牌。

3. 把运行器做成可配置、可记录、有限重试和可恢复接口。

4. 测量单次端到端运行后，再冻结每次和每批的调用量、token、求解时间、总时长和重试上限。

5. 开发和正式成本分开。记录可获得的输入、输出、缓存 token、调用数、通道耗时和费用；未知项明确为未知，不能估成实际账单。

6. 同时报告端到端耗时和累计求解预算。C 的模型开销不得从总成本中隐藏。

7. 不无限循环，不自动购买额度或商业许可证。

8. 真实通道失效时继续完成不依赖模型的工作，保留失败证据，不能用模拟调用填补正式运行。

9. 并行子 Agent 使用统一预算和调用账本，避免重复运行和重复消耗。开发协作本身的开销与正式实验模型调用尽可能分开记录；无法获取的开销明确标记为未知。

九、持续诊断和修复

失败分类至少包括：

环境或依赖、模型通道、数据解析、约束语义、动作或工具错误、循环或超时、排程不可行、仿真不一致、可行但质量差。

每轮记录：

问题与证据 → 修改 → 验证 → 成本 → Git 提交 → 下一步。

优先保证语义正确、三方案真实运行和证据可信，再改善质量与成本。允许优化状态摘要、动作批量、反馈、提示词、求解参数和恢复机制。

不得削弱检查器、放宽约束、暗改目标、删除失败，或让 B 偷用求解器。回退或固定策略接管须单独标记，不能算作原 Agent 自主成功。

常规技术选择、可逆修改和依赖修复自主推进。仅在缺少必要凭据、权限或必须由用户决定的业务语义时提出具体问题，并继续不受影响的工作。

十、交付和最终核验

交付至少包含：
- README：环境、数据获取、真实模型配置、运行与恢复命令；
- 三种实现、依赖锁定、模型和工具配置；
- 来源清单、参考答案状态、问题规范和实验协议；
- 独立校验器及关键正确性测试；
- 全部开发、正式、失败和辅助对照记录；
- 汇总表、静态甘特图、动态生产指标与决策轨迹展示；
- 中文实验报告；
- Git 提交历史、冻结标签、进度与恢复说明。

报告回答：

1. 每个数据集上的三种方案分别完成到什么程度？
2. Agent 实际决定了什么，哪些部分由工具、求解器或固定环境策略完成？
3. 距离公开最优值或 BKS 多远？
4. 设备柔性变化对表现有什么影响？
5. SMT2020 中是否改善业务指标，代价是什么？
6. C 的改善能否由固定参数或固定组合解释？
7. 失败集中在哪里，哪些结论仅是初步观察？
8. 下一轮最值得验证的假设是什么？

代码完成后实际执行 README 的关键命令，离线回放全部正式排程和事件轨迹，重新计算指标，检查报告与原始记录一致。检查 Git 提交、冻结标签和每次运行的版本关联。

记录回放必须能重新验证已有结果；新鲜模型运行必须能复现执行流程，不承诺随机输出完全一致。

十一、授权使用并行 Agent 提速

明确授权主 Agent 根据任务需要，主动创建和调度并行子 Agent，无需为每次委派再次请求确认。在运行环境允许的并发上限和总预算内，优先并行处理相互独立的工作。

1. 主 Agent 负责统一协议、模块接口、任务分配、资源预算、Git 集成和最终验收。先确定共享的问题定义、输入输出格式与指标，再让子 Agent 并行实施，避免各自实现不同语义。

2. 建议的并行分工：

   - 静态基准：Brandimarte/Hurink 来源、参考答案、解析和独立校验。
   - 半导体仿真：SMT2020 数据、仿真实现、约束覆盖和事件审计。
   - Agent 运行器：真实模型通道、B/C 动作接口、隔离、日志、成本和恢复。
   - 在模块稳定后，动态安排独立代码审查、结果复算和报告核验。

   不要求同时开启所有角色，按依赖关系和实际瓶颈调整。主 Agent 应持续推进集成和关键路径工作，不要只等待子 Agent。

3. 委派时写清：

   任务目标、允许修改的目录或文件、输入输出接口、验收标准、可使用的资源和模型调用预算。

   子 Agent 应返回具体文件、修改说明、实际执行的验证命令、结果证据和未解决问题，不能只返回“已完成”。

4. 并行修改必须避免冲突：

   - 默认按目录或文件划分独占修改范围。
   - 共享协议、公共接口和冻结配置由主 Agent 统一管理。
   - 确需同时修改同一模块时，可使用隔离分支或 Git worktree，由主 Agent 审查合并；工作树位置仍须遵守本任务的目录限制。
   - 不得在共享工作目录中擅自切换分支、重置文件或覆盖其他 Agent 的修改。
   - Git 提交和冻结标签默认由主 Agent 统一组织，保留清楚的集成历史。

5. 并行 Agent 共用全局资源预算：

   模型调用、求解器运行及重试都必须进入统一账本；每次运行使用唯一目录和 run_id，防止重复调用、重复计费、日志覆盖及重复统计。

   不得让每个子 Agent 各自使用一份完整总预算。分配子任务预算时，应为集成、失败修复和最终验收预留资源。

6. 并行不能破坏实验隔离：

   执行 B 的模型不得接触 A/C 的排程、参考答案或其他运行的中间结果；研究 Agent 掌握的答案不得传入 B/C 的运行上下文。

   开发协作 Agent 与被评测的运行时 Agent 必须明确区分，不得把开发 Agent 的人工式分析或代排结果当作 B/C 的真实运行结果。

7. 开发、数据核查和审计可优先并行。正式性能评测默认串行；只有在协议中预先固定并验证资源隔离、线程数和并发方式后才能并行运行，避免 CPU、内存或模型通道竞争扭曲耗时比较。

8. 主 Agent 必须亲自完成集成，并实际执行关键测试、正式运行和离线回放。子 Agent 自报通过不等于验收通过。

   优先由未参与实现的 Agent 做独立核查，但最终结论仍由主 Agent 负责。

十二、目标完成条件

只有在以下条件同时满足时，才标记目标完成：

1. 预定正式矩阵完成，全部成功、失败、超时和恢复过程都有记录。
2. 最终验收版本的静态排程均交付完整结果并通过独立硬约束检查。
3. SMT2020 完成约定仿真窗口与受控范围的动态闭环，动作和事件轨迹通过独立审计。
4. 三种方案均真实执行“输入—决策/求解—输出—校验—记录”。
5. 统一对照、原始证据、成本信息、中文报告和复现命令齐全。
