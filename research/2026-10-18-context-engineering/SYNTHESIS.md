## 三份报告的共同结论

1. **没有公开证据表明 LLM 能直接读取我们这个规模的全厂状态并可靠排程。** 已知最大的直接调度实验是 1,000 道静态工序（Starjob，微调 8B，40k 上下文）；我们每周期仅候选就 1,000+ 道，另有约 900 个在加工作业和机组状态。长上下文研究（NoLiMa、RULER、Context Rot）显示标称窗口远大于可靠可用长度，且"逐条处理上千项"比单点检索难得多。
2. **主流 harness 都不把全部状态塞进上下文**，而是"常驻规则 + 导航层/目录 + 按需读取 + 明确告诉模型还有多少没展开"（Claude Code、Cursor、Aider repo map、SWE-agent 的"总行数/省略行数"）。
3. **相关性检索不能保证不漏项**，所以必须另加完整目录和覆盖核对。三份报告独立给出同一设计：可排程工作全集 W 由模拟器确定生成；`validate_plan` 报告 W 中既未排程、也未被模型明确延期的工作。这仍然只报告、不拒绝，与已批准决策"覆盖缺口只报告"一致。
4. **缓存只降成本，不减少上下文占用。** Google 明确写了；OpenAI、Anthropic 的文档可由此推断。按我们的数字，固定前缀全部命中时，未缓存等效输入约 24.6 万，但上下文仍约 75 万。
5. **格式要实测，没有通用最佳格式。** 去掉重复键名能大幅省 token，但准确率可能下降（CSV 在单一实验里少 70% token，准确率低 8 个百分点）。分组（共同属性写一次 + 全部成员列表）和字典编码没有调度场景的公开量化，只能当作待验证的工程方案。
6. **拆分/多 agent 放到后面。** 区域分解在运筹和工业界有成熟做法（分布式 shifting bottleneck、多个 Area Scheduler），但区域之间要交换结构化的协调变量（到达时间、内部交期、瓶颈供料需求），不能靠自由文本。多 agent 会增加总 token 和请求数。
7. **每周期重建上下文、历史外置**（v6 已经这样做：每周期新会话、固定大小的历史摘要）。

## 对 v6 的建议（按优先级）

| 步骤 | 内容 | 是否会丢工作 | 预期影响 |
|---|---|---|---|
| 1 | 固定前缀外移：完整工艺路线和机组静态表改为按 ID 引用，通过 `read_entities` 批量查询；快照只带当前候选需要的路线和资格 | 不丢：静态参考资料可查 | 最大的一项节省，上限约 56 万中的大部分；会增加查询请求 |
| 2 | 完整候选目录常驻：每道可开工工序都有稳定短 ID 和关键调度字段，按"共同属性 + 成员列表"分组；分页给出总数、游标、是否完整 | 不丢：全集可见 | 动态部分（约 19 万）压缩幅度待测 |
| 3 | `read_entities` 加完整性协议：total_count、returned_count、next_cursor、complete；支持多 ID 和字段投影 | 不丢：禁止静默截断 | 减少逐条往返 |
| 4 | `validate_plan` 报告未处置工作：W 减去已排程和模型明确延期（需给出理由）的集合，再加上"有可行工作却空闲且无理由"的机组 | 把静默遗漏变成显式提示；不代排、不拒绝 | 少量反馈 token |
| 5 | 稳定前缀加缓存 | 不影响 | 只降成本 |
| 6 | 以上做完仍超预算，再考虑资源耦合分区（按工序—设备资格、组批兼容性、共享资源划分决策包，单模型一次处理多包）或多 agent | 需要覆盖账本保证各包并集等于全集 | 会增加请求数，影响 E1/P2 对照，需用户决定 |

建议的下一步实验：在真实 mixed_702 状态上，分别测量现状、步骤 1、步骤 1+2 的快照 token 数（o200k），并校验目录覆盖全集（ID 集合相等），再决定是否需要步骤 6。不同表示（紧凑 JSON、分块 CSV、Markdown 表、分组字典）对模型理解准确率的影响，要等 Mac 上能调用模型时再测。
