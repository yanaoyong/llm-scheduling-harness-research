# v6 快照体积分析（编排者实测，2026-10-18）

测量对象：真实 SMT2020 状态。固定部分取自 `env.manifest`；当前状态取 G0 在 t=1649.82 的封存上下文（26 项计划、907 个在加工作业、1,011 道可开工工序）。tokenizer 为 o200k_base。分析脚本的输出在 `/workspace/v6-mac-env/work/`（仓库外）。

## 结论

完整快照约 75.6 万 token，原因是 harness 把模拟器内部数据原样转成 JSON：每行重复字段名、默认值全部写出、相同内容反复出现、浮点数带计算误差、常量说明文字逐行重复。只改表示方式、不删除任何信息，就能压到约 9–12 万 token。

## 快照以外需要处理的地方

1. **快照会被发送两次。** `live.py` 把快照当作提示词发给模型，`get_decision_snapshot` 工具又会返回同一份全文（`mcp_server.py:51`）；脚本化的测试 runner 每个会话第一步就调用它。真实模型如果也调用，上下文会翻倍。应删除这个工具，或改成只返回版本号和摘要。
2. **MCP 会话的每次请求都会重发前面的全部内容。** 一个"读→校验→提交"的会话至少 4 次请求，输入 token 约等于 4 × 快照，再加上工具结果。快照压缩的收益会按请求次数放大，提示缓存（固定部分放在最前、字节稳定）在会话内也能生效。
3. **工具返回没有上限。** `validate_plan` 会返回全部违规（按设计收集所有违规），计划规模大时可能非常长；`read_entities` 按 ID 查询时也没有数量上限（游标分页上限是 512）。应设返回大小上限，并告知总数和截断位置，不能静默截断。
4. **模型输出也有冗余。** 每个任务同时写 `operation_ids`、`lot_ids`、`steps`、`visits`，而工序 ID 本身就是 `批次:工步:访问次数`，23 个任务中全部吻合。去掉后每个任务约从 49 token 降到 32 token。输出 token 单价通常比输入高好几倍，而且模型写得越多越容易出错。
5. **预算闸门只计算了快照。** 实际一次请求还包括 Codex 自带的系统提示、工具 schema、之前的工具结果，以及要预留给输出和推理的空间。闸门应按"整次请求"计算，Codex 自带部分的大小要在 Mac 探针里测出来。
6. **压缩格式需要附说明。** 现在的规则只有 214 token。改用紧凑格式后，必须向模型说明表格约定（空格表示默认值、`=`、区间写法、集合引用），并在 Mac 上实测模型能否正确读懂。调研显示，紧凑格式可能降低理解准确率。
7. **内容取舍要单独讨论。** 以上只改了表示方式。模型是否需要加工节拍、运输时间分布、抽检比例、返工信息，以及 10 条路线的全部 4,013 个工步（还是只需在制品的后几步），这些决定模型能看到什么，需要单独决定。
