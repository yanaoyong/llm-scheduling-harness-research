## 开篇：我的职业经历让我怎样理解这份工作

核心观点：大模型应用工程师要同时组织 Agent 的运行方式、现场工作环境和使用者的协作方法。以冷轧专家排产中的“理解判断—实现规则—现场验证”，连接后续企业知识应用和个人 Harness 实践。第一屏说明这条职业脉络，以及为什么选择智能排程继续探索。

用已有职责支撑观点，避免写成履历列表。冷轧规则的具体故事暂留 M3 缺口，不用行业通用规则替代本人经历。

## 案例一：我怎样检查一个试验是否回答了正确问题

采用 D1：从 2 台设备参与决策、其余 911 台固定出发，说明本人为什么质疑结论，以及怎样推动全厂能力对比。这里展示的是问题判断和实验范围调整；后续建模、实现及结果另行说明。

读者应看明白三个问题：原试验能回答什么、本人指出了什么缺口、后续需要什么证据。不要把扩大范围本身等同于更优结果。

## 案例二：一次受阻的长任务怎样转化为 Harness 工程问题

采用 M1 和 D2，按“任务—卡点—本人决定—Codex 实现—结果与剩余问题”展开：

1. 长时间没有有效提交，后来停在 803.25 秒。
2. 本人要求先诊断重复读页与全量回放，再停止旧会话、交给新会话恢复。
3. 交接物明确为诊断、草稿、检查点、原始记录和累计费用；下一验收点是第二个有效计划。
4. Codex 处理记忆与合法动作的耦合，显式提供页进度与草稿索引；后续仍经历多轮修订。
5. 最终完成一个开发场景的一小时窗口，尚有较高成本和公平比较问题。

由此提出工程职责：上下文供给、任务边界和依赖、状态恢复、工具反馈、按有效进展验收。不要在版本对应确认前写成“只有两次尝试，第二次一次成功”。

## 设计判断：我怎样决定模型、程序和工具各做什么

采用 D3：先补直接排程研究，再讨论职责、复用与公平对照。模型可以参与探索和决策；适合机械验证、状态维护和结果记录的部分交给程序；现场规则和重大取舍由业务人员参与确认。

B/C/离线规则都保留为待比较路线。C-fixed 作为项目提出的后续对照介绍，不能据现有证据归为本人首创或声称已完成该实验。

## 入职后：把现场与使用者一同纳入交付

说明三个同时推进的工作：

- 与排产工程师一起完成正常排产及异常调整，记录判断依据、特殊规则、冲突与缺失条件，形成可维护的规则和案例。
- 用同一任务验证 Harness：给定有效状态和规则，生成建议、核对约束、保留依据，在中断后能正确接续。
- 培训使用者提出任务、管理上下文、检查建议、纠正变化与移交未完成工作；将重复出现的使用问题反馈到产品入口和默认设置。

这些是拟开展工作。若补齐 M3，可用真实冷轧案例解释第一项的方法来源；若补齐 M4，可用同事反馈案例解释第三项。补齐前，可以用已有职责与明确标注的自用案例支持判断，不写成已经完成排程培训。

## 收尾：已有证据、下一步验证和资料入口

用一小段交代当前已验证范围、尚未完成的长期／公平比较，以及下一步如何逐阶段决定是否扩展。附项目状态、代码、试验记录和成本复盘入口，让正文独立可读，技术细节可回查。

下一版的验收重点：个人决策与 AI 实现可区分；每个历史案例能回到来源；没有未确认的业务规则、同事反馈、提效百分比；读者能明确知道“如果加入团队，我准备怎样开始工作”。
