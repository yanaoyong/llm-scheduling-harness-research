# 排程领域的大模型应用：我会怎样着手、推进和判断是否有效

鄢澳勇 · 大模型应用工程方向 · 2026-10-13

如果由我负责排程领域的大模型应用，我会同时推进三条工作线：**Harness 工程**，让 Agent 在可检查、可接续的条件下工作；**现场规则共建**，与排产工程师一起把经验变成可维护的规则和验收依据；**人员培训与持续改进**，让使用者会用，也让系统根据真实使用问题不断改进。三条线围绕同一个真实排程任务推进，互相提供输入：现场规则决定 Harness 要检查什么，Harness 的记录暴露哪里需要培训或改入口，使用中的问题又回到规则和工程上。

这份报告说明这些判断从哪里来、每条线先做什么、和谁协作、交付什么、怎样验证、遇到问题怎样调整。我正在用 Codex 推进的半导体全厂排程探索是主要依据。这个项目**仍在进行中**，下文会写清楚哪些是已经发生的事、哪些是我的计划。

## 一、这些判断从哪里来

| 经历 | 遇到的问题 | 形成的判断 |
| --- | --- | --- |
| 冷轧专家排产 | 系统里已有 MES，部分排产判断仍只在专家经验里 | 规则要先从人那里梳理出来，再写成代码和配置，并和现场人员一起测试 |
| 企业知识库交付 | 甲方服务只给有限的上下文空间 | 上下文是要设计的：拆分任务、组织知识、分配模型 |
| 法律政策 RAG | 结果不对，原因可能出在检索、推理或评价任一环节 | 先定位错误出在哪个环节，再改对应环节 |
| 个人 Harness | 知识工具建好了，Agent 仍会绕开它自己 grep | 工具存在不等于被使用，要观察实际行为再改设计 |
| 排程探索 | 试验“跑通”却回答不了要问的问题；Agent 持续运行却没有推进 | 先确认实验在回答正确的问题，再以可核对的有效进展来验收 |

排程探索里有三个决定最能代表我的做法：

- **质疑试验范围。** 早期试验只让 913 台设备中的 2 台参与决策，其余固定。我问“凭什么固定 911 台”，因为这样三种方案可能都没有决策空间，比较就没有意义。之后我把目标定为全厂能力对比。
- **停止空转，带状态恢复。** 见下一节。
- **先研究，再设计。** B 取得进展后，我没有因此锁定路线：先补充“用大模型直接排程”的调研，再讨论模型与程序怎样分工、B/C/离线规则怎样公平比较。

在这个项目里，建模、代码实现和实验运行大部分由 Codex 完成。我负责的是：提出问题、决定优先级和取舍、规定交接内容和验收点、审查结果是否真的证明了想证明的东西。

## 二、工作线一：Harness 工程

### 为什么一次跑通不够

全厂排程中的 B 方案由模型直接决定排程。它曾经运行了近两小时还没有提交第一个计划，后来又停在仿真第 803.25 秒，只提交了一个有效计划。这个过程中我做了几件事：

1. 把“进程还在跑”改成“有没有可核对的有效产出”来判断，追问它是否在空转。
2. 把诊断和实施分开：另开会话诊断，优先查重复读页、每轮全量回放和记忆超限，并保留原始记录。
3. 规定恢复的顺序和交接内容：先修模型通道，再从 803.25 秒接续，复用已有草稿，不重复执行，保留费用记录。
4. 停掉旧会话，把诊断结论、草稿和检查点交给新会话，把“第二个有效计划”定为下一个验收点。我也同意把同一模型已提交的完整基准计划放进后续提示，减少重复查询。

诊断发现，问题出在应用协议，而不是模型上下文不够：记忆字段一旦超限，同一轮里合法的查询也被一起拒收；下一轮只看到错误信息和旧记忆，于是重新去读上一页。Codex 随后把超限记忆的拒收和合法动作分开处理，并在提示里直接写明“已读到第 12 页、下一页是 13”和已保存任务的索引。恢复后出现了第二个有效计划提交，但同一时间仍发现反馈链有问题。之后又经过多轮修订，才完成一个开发场景的 0—3600 秒窗口：95 次计划提交，来源、物理和模型输出归属审计通过。

这不是“失败一次、改一次就成功”。整个开发过程用了 1,362 次模型尝试、约 4,467 万 tokens。后期协议稳定段的 779 次调用里，输入占 96.77%，平均每次提交需要 9.74 次调用。所以我的结论是：通用 Agent 能偶尔跑通，但上下文怎样供给、进度由谁记、交接带什么、什么算有效进展，如果都靠人临场修正，就既不稳定也不经济。这些都应该成为 Harness 的工程职责。

### 模型、程序、求解器和人各做什么

| 角色 | 负责 | 原因 |
| --- | --- | --- |
| 模型 | 理解任务、在候选之间权衡、规划下一步、组合工具、根据反馈修订 | 这部分需要灵活判断，也是要检验模型价值的地方 |
| 确定性程序 | 读取状态、校验字段与约束、维护版本和草稿、记录提交与回执、拒绝不合法动作 | 能被精确核对的事不该交给模型，也不该让程序替模型悄悄补值或择优 |
| 求解器 / 经典算法 | 作为基线（A），或作为模型可调用的工具（C） | 它的效果已知；模型是否带来增益，要和它在同样条件下比较 |
| 人 | 确认目标优先级、现场规则和例外、关键取舍，审核后决定是否执行 | 规则和取舍的责任在现场，Agent 只给建议 |

我提交的首轮任务书已经写明：工具可以查询、计算、检查和反馈，但不能用求解器或预先算好的答案替 Agent 做核心决策；失败不能删掉，回退方案也不能计为原方案成功。最终 B 的求解器调用为 0，所有实际派工都能追溯到模型的明确决定。

### 我会处理的八个工程问题

| 问题 | 在排程实验中看到的 | 我的做法 | 怎样验证 |
| --- | --- | --- | --- |
| 任务拆分 | 诊断需要另开会话，交接内容要靠我逐条指定 | 每个任务写清输入、输出、依赖、验收点和预算；只把能独立完成的部分拆给其他执行者 | 交接后能否直接继续，有没有重复或遗漏 |
| 上下文供给 | 进度靠模型自己记，结果反复重读 | 进度、已确认事实、草稿索引由程序明确提供；长期规则按版本管理；原件可以回查 | 重复读取次数；必要约束有没有丢失；提供的信息是否被实际使用 |
| 工具接口 | 一次提交被拆成很多轮往返 | 查询、生成、检查、提交的职责分开；纯机械步骤合并成一次原子操作 | 每次提交的调用次数和 token 下降后，决策质量有没有变差 |
| 状态与草稿 | 恢复时要人工指定带上草稿、检查点和费用记录 | 候选、检查结果、已提交动作和剩余工作单独保存，并绑定状态版本 | 状态更新后旧候选会不会被误用 |
| 检查点恢复 | 换会话恢复依赖人工整理交接 | 从检查点接续；提交结果未知时先核实回执，不自动重发 | 人为中断后能否正确接续，有没有重复执行 |
| 失败反馈 | 停止原因没有传给下一轮，可能再次空转 | 校验失败要附带可供修订的具体原因；记录所有失败 | 同一类失败是否重复出现 |
| 权限边界 | 需要防止程序暗中替模型做决定 | 分清只读查询、生成建议、提交执行；执行需要明确授权和人工审核 | 抽查每个动作的来源与授权记录 |
| 效果评估 | 只看“完成了”会掩盖成本和质量问题 | 同时看合法性、排程质量、响应时间、全部尝试的成本、人工介入次数 | 用同一组案例比较改动前后 |

### 用实验选择方案，而不是先定方案

两轮调研之后，B（模型直接排程）、C（模型调用工具）和离线规则生成三条路线都保留着。我要求先讲清它们怎样公平对照。目前讨论中的方案是让三者共用同一套状态、校验、执行和评价流程，只替换“排程决定怎样生成”这一部分；我认同这个方向，因为这样比较的才是决策方式本身。这个方案还没有定稿。项目记录里还提出了 C-fixed 对照：用同样的工具和预算，固定参数、不调用模型。只有 C 明显优于 C-fixed，才能说模型带来了额外价值。最终选哪条路线，要看同等条件下的质量、成本、响应时间和人工负担，以及现场对实时性的要求。

### 先做什么、和谁协作、交付什么

1. **先做什么。** 用一个真实排程任务打通最小路径：读状态 → 澄清任务 → 模型生成候选 → 程序检查 → 人工审核 → 提交并留档。然后再用上下文过长、规则冲突、工具超时、状态变化等情况测试它。
2. **和谁协作。** IT/MES 负责可信的状态接口；排产工程师提供规则和审核；我负责 Harness 设计和评估；代码实现可以由 AI 辅助，我负责验收。
3. **交付什么。** 任务模板与交接格式、状态和草稿存储、工具接口说明、检查与回执记录、回放用的案例集，以及评估报表。
4. **遇到问题怎样调整。** 先看记录，判断问题属于上下文、工具、状态、规则还是模型能力，只改对应的那一层；改完用同一组案例复测。成本降低后，要复查决策质量没有变差。

## 三、工作线二：现场规则共建

### 为什么

排产里最关键的往往不是写在制度里的规则，而是工程师在特定情况下的判断。这些判断不先梳理出来，Agent 给出的建议就会“合法但不能用”。冷轧项目让我形成了这个工作方法：和专家一起梳理排产判断，写成规则逻辑和数据库配置，再和现场人员一起测试。半导体工艺和约束我还需要重新学习，所以入职后我会从观察开始。

**下面这些是入职后的计划。** 能支撑这个方法的已有经历，是冷轧项目中“梳理判断 → 实现规则 → 现场测试”的职责。

### 先做什么、和谁协作

1. **观察。** 选一个边界清楚的设备组或重排任务，跟着排产工程师完成几轮正常排产，记录他看哪些信息、按什么顺序判断、为什么这样安排。
2. **参与。** 用同一份输入，让 Agent 给出建议，和工程师的方案并排比较。重点追问插单、停机、质量挂起、临时资格变化这类特殊情况。我不预设目标工厂的规则，一切以现场核实为准。
3. **复盘。** 双方方案不一致时，固定输入和规则版本，再判断差异来自哪里：信息缺失、规则没有表达出来、目标冲突、模型推理错误，还是工具实现问题。仍然没有共识的情况，记为“待确认案例”，交给对应的业务负责人裁决。聊天里随口的一句补充，不能直接变成长期规则。

协作对象包括：排产工程师（日常判断）、工艺或规则负责人（例外裁决和规则审批）、IT/MES（数据和接口）。

### 交付什么

每条规则整理成一张可维护的规则卡：

| 字段 | 内容 |
| --- | --- |
| 适用范围与依据 | 哪些产品、设备、工步适用；来自谁；何时生效 |
| 条件与例外 | 需要哪些状态；必须满足什么；哪些情况例外 |
| 冲突与缺失 | 与其他规则矛盾时由谁裁决；信息不足时怎么处理 |
| 验证案例 | 正常案例、反例、特殊情形；预期结果及认可人 |
| 维护 | 负责人、有效版本、更新方式、受影响的测试 |

规则卡再按用途落到不同位置：硬约束进入程序校验；经验和历史案例进入按需查阅的资料；目标优先级和一次性例外由任务入口填写；实时状态来自业务接口。工程师确认过的案例集，就是 Harness 回放测试的验收依据。

### 怎样验证、怎样推进

- **离线回放。** 用历史案例回放，看 Agent 建议与工程师方案的差异，以及差异的原因构成。规则被违反的情况必须为零，其余差异要能解释。
- **只读影子运行。** 和现场排产并行，只给建议、不执行，记录工程师接受、修改和拒绝的原因。
- **限定场景辅助。** 只在规则覆盖完整的场景中，经人工审核后执行。

每一步是否进入下一步，看的是验收条件，而不是时间表。如果某类差异反复出现，先补规则卡或案例，再继续推进。

## 四、工作线三：人员培训与持续改进

### 为什么

Agent 用得好不好，一部分取决于使用者给的信息是否完整，一部分取决于系统有没有把正确的信息和选项放在面前。所以我不会把问题都归到“使用者不会提问”：能由系统保障的，例如状态版本、约束检查、交接记录，就不应该靠人记住。

### 使用者需要学会什么

| 动作 | 具体要求 |
| --- | --- |
| 提出任务 | 说清目标、范围、时限和不可改动的安排；区分“只要建议”和“需要执行” |
| 提供现场状态和约束 | 选用经过确认的状态快照；说明临时停机、插单等变化；区分确认事实、假设和一次性例外 |
| 管理上下文 | 新任务开新任务；延续任务时只带目标、关键约束、已提交动作、未决问题和来源，不把整段聊天反复粘贴 |
| 核对建议 | 检查受影响的批次、依据、假设和取舍；查看程序检查结果和未解决项 |
| 纠正错误 | 指出具体哪里不对；条件变化后重新确认目标，让系统刷新状态、重新检查旧候选 |
| 移交未完成任务 | 交代当前状态、已完成动作和未完成事项，确保接手的人不会重复执行 |

举个例子：设备组临时停机，需要调整本班还没开工的批次。使用者选择确认过的状态快照，指定交期目标和冻结的安排，声明“只要待审核的建议”。停机恢复时间还不确定时，就保持“待确认”，不让 Agent 去猜；恢复时间一旦明确，就告诉系统发生了变化，系统刷新状态、重新检查之前的候选。

培训方式是共同操作 → 引导练习 → 独立完成案例 → 复盘。排产人员重点学提任务和判断结果；规则负责人重点学例外确认和规则维护；技术人员重点学诊断和恢复。

### 我怎样观察和改进

我会记录：哪些建议被拒绝、拒绝的原因、使用者反复补充的信息、人工接管的次数、交接后是否出现重复动作。问题按来源分类后，分别处理：

- **入口问题。** 必要信息总被漏填，就改任务表单和默认值。
- **上下文供给问题。** Agent 没有用上已提供的信息，就改供给方式。个人 Harness 的自用验收里遇到过这种情况：Agent 说要查 Wiki，实际却用 grep。改成委派前先预查、把结果放进任务材料之后，复测出现了正例，但还谈不上 Agent 会稳定自主采用。
- **规则缺失。** 回到工作线二，补规则卡和案例。
- **模型能力。** 回到工作线一，调整职责划分或方案路线。
- **使用方法。** 只有确实属于使用方法的问题，才补充到培训和操作指引里。

每次改动都要验证：用同一组任务案例，对比改动前后的完成情况、补充信息次数和接管次数；看受训人员能否独立完成新案例、发现异常并说明判断依据。

已有经历方面：我的个人 Harness 以团队形式分发给公司人员使用，也有自用改进和验收记录。目前没有可核实的同事反馈链、团队采用率或提效数据，所以这里不把它写成团队成果。

## 五、三条线怎样一起推进

| 阶段 | Harness 工程 | 现场规则共建 | 培训与改进 | 进入下一阶段的条件 |
| --- | --- | --- | --- | --- |
| 1 共同梳理 | 确认接口和状态来源；定任务模板 | 观察和参与排产，形成第一批规则卡和案例 | 和工程师一起确认任务入口需要填什么 | 试点范围明确，关键状态可获取，验收目标经工程师确认 |
| 2 离线回放 | 打通最小路径，测试中断恢复 | 用案例集回放，分析差异原因 | 让工程师试用并记录困惑 | 规则违反为零，差异可解释，恢复正确，成本和响应时间在可试用范围内 |
| 3 只读影子运行 | 并行运行，只出建议，全程留档 | 收集被拒建议，补充规则和例外 | 开展正式培训，观察实际使用 | 工程师能核对和解释结果，发现异常时能正确接管 |
| 4 限定场景辅助 | 审核后执行，权限分级 | 根据新问题更新规则版本 | 根据使用记录改入口和指引 | 业务价值、运行成本和维护责任都经各方确认后，再考虑扩大范围 |

不满足条件时，就停在当前阶段，或退回上一阶段处理。具体周期要在了解现场需求、数据和接口条件后再定，我不预设工期或收益。

## 六、目前已证明和尚未证明的

**已经发生的：** 模型直接排程方案 B 在一个开发场景中完成了一小时仿真窗口，承担 913 台设备的排程责任（841 台实际发生派工），各项审计通过；失败和成本记录完整保留。

**尚未证明的：** B 是否优于经典算法或 C；8 小时、24 小时等长窗口表现；经济性和实时性；在真实工厂中的收益。Harness 的整体方案仍在讨论阶段，还没有定稿和编码。现场规则共建和人员培训是入职后的计划。
