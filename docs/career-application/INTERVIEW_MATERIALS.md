## M1：可以还原的受阻与恢复案例

### 任务与卡点

任务是推进 SMT2020 全厂 A/B/C 排程探索，其中 B 由模型直接决定排程。在一小时开发窗口的推进过程中，用户先发现 B 跑了近两小时还没有首个计划提交，要求核查是否重复调用；后来运行停在 803.25 秒，只有一个已提交计划，需要继续完成 0—3600 秒窗口。[S01](evidence/2026-10-13/source-excerpts.md#s01)、[S06](evidence/2026-10-13/source-excerpts.md#s06)、[S12](evidence/2026-10-13/source-excerpts.md#s12)

当时助手报告的一个具体机制问题是：记忆更新与工具动作共用拒绝门槛，记忆超限会使下一页查询也作废；下一轮只看到错误和旧记忆，容易再读上一页。这是应用协议和进度供给问题，不能概括成“模型总上下文不够”。[S06](evidence/2026-10-13/source-excerpts.md#s06)

### Codex 随后实现了什么，结果到哪一步

V9 将超限记忆的拒收与合法动作处理分开，在提示中加入绑定快照的读页记录、缓存引用和草稿任务索引。恢复首轮可直接看到“已成功读到第 12 页、下一未读页为 13”及 20 条已保存任务，减少靠自由记忆重述进度的依赖。[S07](evidence/2026-10-13/source-excerpts.md#s07)、[S08](evidence/2026-10-13/source-excerpts.md#s08)

后续还有观测代码的元组哈希错误、目录响应缺少 `status` 字段等故障，说明修复并非一次完成。[S09](evidence/2026-10-13/source-excerpts.md#s09)、[S10](evidence/2026-10-13/source-excerpts.md#s10) 用户也同意把同一模型已经提交的完整基准计划放进后续提示；这支持“用户确认上下文供给调整”，不能把助手提出的具体方案全算成用户原创。[S11](evidence/2026-10-13/source-excerpts.md#s11)

最终 B 在一个开发场景完成 0—3600 秒，累计 95 次计划提交，913 台设备属于责任范围，841 台实际发生派工。整个开发沿革含 1,362 次模型尝试、44,666,702 个已知输入输出 tokens，另有 3 次历史用量未知。它支持“恢复后能够推进并完成该开发窗口”，不支持“只改一次上下文就成功”“完整项目完成”或“已证明具备现场经济性”。[S12](evidence/2026-10-13/source-excerpts.md#s12)

### 可以放进后续报告的叙述草稿

> 在这次排程探索中，我发现仅仅让 Codex 持续工作，并不能保证任务持续推进。我先要求核查 B 为什么长时间没有有效提交，再把诊断与实施分开：把重复读页、全量回放和记忆超限列为优先修复项，要求新会话拿到原草稿、检查点和完整调用记录，从已完成的位置继续，并以新的有效计划作为验收点。具体协议修复由 Codex 实现。后续多轮修订完成了一个开发场景的一小时窗口，但成本仍高。这让我把上下文供给、任务交接、状态恢复和进展判断都纳入 Harness 的工程职责。

这段草稿对应上面的恢复链。本人此前提到的“第一次失败、第二次改动后成功”是另一条概括性陈述，[S00](evidence/2026-10-13/source-excerpts.md#s00) 尚未指明版本。后续只需核对：它是否就是上述换会话恢复过程；若是另一轮，补充那轮任务、失败点和改动，不强行合并两个故事。

## M2：优先选用的三个个人决策

### D1：质疑局部试验能否回答全厂能力问题

- **背景：** 早期 SMT2020 试验只有 2 台设备由方案决定，其余设备采用固定规则。
- **用户原话：**“那你凭什么固定了911的机器呢？不能说你想固定就固定，并且你没有依据的固定是否会导致剩下的2台的排产基本上没有活动空间导致三个方案得不到比较”。[S13](evidence/2026-10-13/source-excerpts.md#s13)
- **随后选择：** 将“A/B/C 的全厂排程能力对比”作为优先目标；这是用户对助手问题的明确选择。[S14](evidence/2026-10-13/source-excerpts.md#s14)
- **可归属本人：** 识别实验控制范围与想回答的问题不匹配，推动扩大验证范围。不能把后续 913 台设备的全部建模和实现归为本人完成。
- **可用表述：**“我质疑过一个看似已经跑通的试验：只让两台设备参与决策，其他设备固定，可能使三种方案都没有足够决策空间。因此我要求转向全厂能力比较，而不是直接接受局部结果。”

### D2：停止空转，带状态恢复，以有效提交验收

- **背景：** B 长时间无有效提交，后又停在 803.25 秒。
- **本人决定：** 要求诊断重复读取、更换实施会话，交接草稿、检查点、历史记录和费用，先验证下一次有效计划；不是单纯增加等待时间。[S01–S05](evidence/2026-10-13/source-excerpts.md#s01)
- **可归属本人：** 问题优先级、交接范围、验收节点和记录保留要求。具体状态结构、缓存、V9 代码与回归检查由 Codex 执行。
- **可用表述：**“我将‘任务还在跑’改成‘能否出现可核对的有效进展’来判断工作，并要求带着已完成状态继续。失败记录和费用也随恢复链保留。”

### D3：先补研究上下文，再决定 Harness 和 B/C 路线

- **本人要求：** 先了解并使用已有 M0.5 调研方法，获得充足上下文后再设计 Harness。[S15](evidence/2026-10-13/source-excerpts.md#s15)
- **具体扩展：** 主动加入“大模型直接排程”专题，并指出它关系到 B 或 C 的路线选择；分配 Luna 做拆题、检索、提取，Sol 做核验、综合、评审。[S16](evidence/2026-10-13/source-excerpts.md#s16)
- **讨论边界：** 先讲清模型决策和机械操作、可复用能力、公平比较，暂不急着写代码。[S17](evidence/2026-10-13/source-excerpts.md#s17)
- **可归属本人：** 研究顺序、新增主题、角色和预算选择、设计讨论范围。研究综合与具体接口方案由 AI 辅助产出；路线尚未最终定稿。
- **可用表述：**“我没有因为一次直接排程能跑通就把路线锁定。我要求补充直接排程研究，再结合已有代码讨论 B、C 和离线规则怎样公平比较，先明确职责再实现。”

### 用户举的另外三个例子，怎样归属更准确

| 候选说法 | 现有证据 | 可以怎样讲 |
|---|---|---|
| “我坚持做模型输出归属审计” | 用户提交的首轮任务要求 B 的核心决策不能被求解器、最优答案或固定启发式替代；结果报告记录归属检查通过。S19、S12 | 可说“我提交／采纳了这项验收约束，要求分清模型与工具贡献”；不能直接说本人原创审计机制或亲自实现审计器 |
| “我不把失败改写成成功” | 用户任务要求不删除失败、不把回退计为原方案成功；后续本人要求保留原记录和费用；结果报告保留旧失败。S19、S04、S05、S12 | 可说“我要求恢复时保留失败、草稿和成本，旧段不因修复而变成成功”；具体记录机制仍需归给实施过程 |
| “我提出 C-fixed” | 现有摘录中，C-fixed 明确出现在助手的下一轮建议，用户另有公平比较的宽泛要求。S18、S17 | 当前不能归为本人首创；可说“项目后续提出了 C-fixed 对照，我希望据此检验模型增益”。如本人确实先提出过，需要补更早的原话或材料 |

首轮长提示的作者来源没有充分证据。`role=user` 只能确认用户提交了该内容，不能据此认定每项设计都是独立原创。上述 D1–D3 优先采用较短、明确且带上下文的本人追问或选择。

## M3：冷轧隐性规则或特殊情况

已确认：本人参与与专家梳理排产判断、编写 C++ 规则逻辑及数据库配置、实现 MFC 页面，并与现场排产人员进行功能和业务测试。但现有职业指南在 C06 明确写明，没有保留一条包含参数与例外的完整规则。[S20](evidence/2026-10-13/source-excerpts.md#s20)

## M4：同事使用反馈与对应改动

已确认：个人 Harness 自用，也曾以团队形式向公司人员分发，采用人数与团队效率未知。现有材料还专门澄清，“大家都没有采用该方法”指外部项目通常以 Skill 组织方法，不能理解成公司人员没有使用。[S21](evidence/2026-10-13/source-excerpts.md#s21)
