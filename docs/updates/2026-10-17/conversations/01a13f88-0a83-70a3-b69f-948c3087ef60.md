- 当前触发未覆盖需求的机组。
- 已有待执行任务、冻结承诺或等待安排涉及的机组。
- 根据公开预测，在窗口内可能可接单，且有对应就绪任务的机组。

第一版重点解决“**工件已经就绪，但机组还忙，所以可以预先安排下一单**”。不把所有条件后继都展开，更不要求模型遍历全厂。

上下文可以组织成下面几块，用它替换现在只围绕触发族的 48 行预览：

| 内容 | 必须让模型知道什么 |
|---|---|
| 本轮范围 | 当前时间、状态版本、触发原因、前瞻窗口、实际纳入范围 |
| 近期机组 | 编号、加工族、忙碌/停机状态、名义可接单时间、预测局限、换型状态、连续加工限制、已有队列 |
| 就绪候选 | 工序及批次身份、可用机组、就绪状态、优先级、交期、等待时间、加工/占用时间、批量与换型要求、资格或绑定约束 |
| 已有承诺 | 待执行任务、机组顺序、冻结任务、已派工任务；明确哪些需要保留或处理 |
| 条件工作 | 单独列出可能近期到达的后继及不确定性；与已经就绪的任务分开 |
| 完整性与反馈 | 哪些事实完整、哪些未展示、定向读取入口；最近几轮实际执行情况 |

**同一批候选只出现一次。** 例如第 136 轮，六台 Dielectric 机组共享的 74 个候选只给一份，再表达各工序允许哪些机组。这样既减少重复，也提醒模型：这些机器在竞争同一批任务，不能重复分配。

资格不确定、绑定关系、批量下限等影响合法性的字段必须保留；不能为了压缩，把它们概括成一句“可加工”。

避免再次变成全厂扫描，需要同时约束上下文生成和模型取数：

1. **由程序筛选时间范围、关联候选和去重。** 程序可以遍历已有公开状态，但不让模型通过多次调用完成这项机械工作，也不替模型选生产任务。
2. **默认提供足以做决定的事实。** 不只给“747 有 74 个候选”，然后要求模型再逐个恢复详情。
3. **补读必须针对具体缺口。** 例如某候选的绑定来源不明确，就查该工序及相关机组；不因为看到一个加工族就把整个工厂重新读一遍。
4. **超量时明确缩小范围。** 先压缩共享字段；若仍放不下，可缩短前瞻窗口，并告知实际覆盖范围。当前缺口和已有承诺始终保留。不要静默截取前 48 个，也不要要求把所有省略页读完才能提交。

相应的核心提示词，我建议写成这样，放在现有工具协议前面：


这里还要处理两个容易遗漏的细节。

**一是已有队列的维护。** 当前协议下，待执行任务的 `not_before` 如果已经落到过去，不能直接原样 `keep`，需要模型显式处理。默认上下文应直接列出这些任务及原因，避免多任务计划下一轮因维护问题被拒绝。

**二是反馈要衡量实际覆盖。** 最近三轮展示“推进了多少模拟秒、实际派工多少项、因什么需求再次停止、用了多少调用”；当前轮展示“已读取几次、是否已有提案”。排了十项但一项没执行，不能当作效率提升，也不需要为总结反馈另开一次模型调用。

**不只有 prompt，但上一版确实没有从系统层面保证“模型会考虑更多任务”。** 这点需要区分清楚。

| 层面 | 上一版建议 | 能保证什么 |
|---|---|---|
| Harness 整理上下文 | 程序筛选近期机组、关联就绪任务、去重并保留约束 | 保证相关事实进入输入，不需要模型自己扫全厂 |
| 提示词 | 要求联合规划、定向补读、避免只补当前缺口 | 引导行为，不能保证执行 |
| 系统反馈 | 自动统计实际推进时间、派工数、调用数和重排原因 | 保证反馈准确，不能保证模型据此改进 |
| 现有计划校验 | 检查任务合法性、重复分配、已有承诺等 | 能拦住部分非法计划，**不会因为遗漏近期工作而提醒它** |

所以，如果我们希望减少对 prompt 的依赖，我建议再加一个明确的系统机制：**提交提案时，自动检查这份计划对近期资源的覆盖情况。**

例如模型仍只给 312 排一个任务，`propose_delta` 的返回结果就同时指出：

> 当前触发需求已覆盖。  
> 747 等近期资源尚无待执行任务，且关联的公开就绪候选仍未被分配。  
> 这些是待考虑的覆盖缺口；机器释放时间属于预测。

这个检查由程序计算，**不增加一次模型调用，也不替模型选择任务**，直接放进原本的提案检查结果。模型在已有的下一次调用里，可以修改计划，或者明确确认为什么暂不覆盖。

但这里不能简单做成“没给每台机器排任务就拒绝”：

- 多台机器可能竞争同一个工件，不能重复安排。
- 某些机器已有足够队列。
- 某些后续工作存在资格或路线不确定性。
- 有时保留资源给更重要的任务是合理选择。

因此，我建议的组合是：

**系统负责提供相关事实、检查覆盖缺口；模型负责生产选择和解释取舍；执行器负责实际合法性。**

上一版主要补了第一项，第二项还不够。若只新增上下文、再写一句“请多排一些”，模型仍可能继续只排一项；加入提案后的覆盖检查，才能让这种遗漏在提交过程中被明确暴露。它仍不能保证排程质量改善，但比完全依赖 prompt 更可检查、也更容易定位失败原因。
