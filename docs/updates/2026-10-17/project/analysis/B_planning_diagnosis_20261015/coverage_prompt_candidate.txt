DRAFT FOR AN ISOLATED FOLLOW-UP EXPERIMENT. NOT APPLIED TO THE LIVE B RUN.
Append this planning guidance to the existing protocol; keep its ownership, exact identity, validation, freezing, physical execution and explicit apply requirements.

Your decision unit is a rolling factory plan. A trigger identifies the first currently uncovered demand; it does not define the full scope of this revision. Preserve the production objective and legality. As a secondary efficiency goal, reduce repeated model calls needed to cover known work. Do not improve the call metric by withholding useful work, hiding an uncovered machine, adding artificial waits, or scheduling invalid tasks.

For this development variant, inspect a nominal coverage window of min(current_time + 300 seconds, observation window end). This is a planning target, not a guaranteed execution interval or a minimum number of tasks. No private future event or exact completion may be inferred from it.

Before submitting, inspect both current uncovered resources and resources that may become available within the window using public machine availability forecasts. The family catalog alone does not contain machine availability. With the existing tools, use read_entities with machine catalog cursors and selected fields to inspect the factory; follow next_cursor for completeness. Group resources from those facts yourself. Batch independent machine, operation and pending-task queries in a single read_entities action when they fit. Use smaller projections and pagination when required. Do not repeatedly query only the machine that caused this trigger.

Distinguish these kinds of work:
1. Currently ready operations, including lots waiting for machines that are busy now. Where useful, explicitly choose several compatible tasks, batches and machine orders so those machines have work when they become available. Consider the effect of reserving a lot on competing machines.
2. Public nominal successor operations. conditional=true means future or not yet ready; it does not by itself mean an illegal operation. Inspect predecessor, sampling/rework, qualification and binding facts before deciding whether to plan it. A deterministic-looking own step does not prove that its predecessor path is certain.
3. Genuinely unresolved branches or missing qualifications. Explain the evidence needed and preserve necessary event-triggered replanning. Do not invent an outcome to fill a queue.

not_before is an earliest-start condition; the executor also checks actual lot and machine readiness and your submitted machine order. A forecast of now + 1 second is not an exact imminent completion. Do not create one- or two-second plan validity merely to poll it. Under the CURRENT protocol, a retained non-frozen pending task whose not_before is in the past requires your explicit replacement or cancellation; handle those records without resubmitting dispatched work.

One propose_delta can contain multiple tasks on multiple machines, including ordered follow-on tasks. 'One action' does not mean 'one production task'. 'Small revision' refers to serialized response size. Use the multi-call draft tools only when the complete response really is too large. Choose valid_until to support the intended coverage and any real uncertainty; validity alone is not coverage.

Before applying a checked candidate, assess whether it addresses the current demand and the near-term resources you inspected. A one-task plan is valid when the facts justify it, but do not use it by default. In the existing reason or selection_note, briefly record the intended coverage, deferred groups and factual reasons, and any unresolved uncertainty. Do not output extra schema fields.

Keep exact lot, operation, visit, machine, batch and order choices model-authored. The host still performs mechanical checks only. This draft adds no constructor, solver, ranking, automatic selection or silent schedule repair.
