## 2. 用户在 2026-10-18 做的决定

原则：分三层——物理事实、展示规则（须用户批准）、调度决定（只属于模型）。展示规则若隐藏工作，就等于替模型做了调度决定。

| 项 | 决定 | 实施位置 |
|---|---|---|
| 可见范围 | 用**物理时间窗**取代"每 lot 固定看 2–3 步"和"按均值预测的 H 筛选"：沿路线累加可证明的最短时间，最早可能开工 ≤ now+W 的工序全部导出并展示；W = 登记的 H（默认 900 s）。导出集合取"时间窗 ∪ 原 lookahead"，现有可提交工序一个不少 | `physical_window.py`、`observation.py`、`snapshot.py` |
| 时间标签 | 模型看到的内容里不再有 `release_time=now` 占位；改为 `earliest_start`（可证明下界）、`nominal_start`（均值，仅供参考）；已排队的工序另给 `waiting_since` | `physical_window.public_operation`、`facts.py`、`prompt_rules.py` |
| 资格 | 删除 `qualification_uncertain`。模拟器只在存在绑定记录时才限制机台；初始 WIP 没有记录，因此不受限制。已观察到的绑定和 `same_machine_as` 照旧 | `observation.py`、`ledger.eligible` |
| 空闲判定 | 机器的加工槽已满时不算空闲（非 cascading 1 个槽，cascading 2 个）；贪心见证明确标为下界 | `ledger.idle` |
| 字段 | 新增 `priority`、`waiting_since`、`processing_seconds_min/max`；`setup_transitions`、`min_runs` 进入静态前缀；`unavailable_intervals` 为空表示"未提供数据" | `snapshot.py`、`observation.py` |
| 交期 | 预设上限：G0 dense 增量 ≤ 8,000 才启用。lot→due 映射实测 10,676，**未启用**（待决，见 §5） | `snapshot.py`，开关默认关 |
| 诊断 | 队列阻塞、引用缺失工序的旧任务（如 G0 的 `d43-g`）显示在下一锚点的快照/回执中；**不新增唤醒、不自动取消/跳过/改序**。未覆盖清单可通过 `coverage.complete_read` 完整分页读取；read_entities 新增 gt/gte/lt/lte | `physical_window.queue_diagnostics`、`submit.py`、`facts.py`、`mcp_server.py` |

- G0 的 upcoming 从 74 行变为 172 行（执行中 135 行，后续链 37 行）。

- **物理时间窗覆盖率**（t=0 起，原生模拟器真实前推 1 小时）：

  | 实际开工时间 | 原白板可见 | 时间窗可见 |
  |---|---|---|
  | 15 分钟内 | 100% | 100% |
  | 30 分钟内 | 54% | 100% |
  | 1 小时内 | 46% | 100% |

- **封存分类未变**：去掉资格排除后，86 个封存观测里没有新增任何"可开工-空闲机"配对，因为对应机台的其他条件（忙碌、绑定、min-run）本来就已排除它们。t=0 统计里空闲见证从 808 变为 815，说明改动确实生效。

## 4. Mac 端执行顺序

所有命令在 V6 目录执行，产物写 `$WORK`，详细参数见 `MAC_RUNBOOK.md` 对应步骤。步骤 0–4 不调用模型。

| 步骤 | 做什么 | Phase T 后的变化与通过标准 |
|---|---|---|
| 0 | 拉取 `main`，执行 preflight | 检出 `main`（不再是 `feat/harness-v6-codex-runner`）；preflight 全部 PASS |
| 1 | 构建公共/封存夹具与题集 | 按 RUNBOOK 步骤 1 生成 `p2.json`、`e1.json`、`hour.json` 及附属证据；题集使用 `p2.json.ledger.jsonl.gz`。四状态 384 题、16 个请求，upcoming 题考 `earliest_start`；三份物理回放都是 configured suite 的必需输入 |
| 2 | 离线 suite（plain + configured） | plain 与 configured 全部通过；封存分类应与 Q/R 一致（或逐字段解释差异）；`measure_physical_window.py` 为 0 violations；G0 dense 当前状态约 54.6k（比 43,817 多出不超过 20,000） |
| 3 | 固定二进制的本地 mock 探针 | 同 RUNBOOK |
| 4 | 请求开销录制与登记 | 用 Phase T 的快照重新录制；旧快照下的开销值不能沿用 |
| 5 | A/B 理解（**开始调用真实模型**） | 比较 explicit 与 dense 两种格式，重点看新时间标签的误读率：模型是否把 `earliest_start` 当成确定到料。需要预算授权 |
| 6 | 真实物理 scripted dry-run 与一次会话 smoke | 同 RUNBOOK；确认 blocked_queues / absent_operation_tasks 只在锚点出现，没有新增唤醒 |
| 7 | 填全并验证登记 | Δ 先按 §5 的决定登记 |
| 8 | E1/P2 各三条轨迹 | 需预算授权 |
| 9 | 汇总与回传 | 回传 `$WORK` 中各步骤指定的文件 |

注意：MAC_RUNBOOK / MAC_VALIDATION 末尾"Phase T 最终离线核验"一节用的是开发机路径（`/workspace/v6-mac-env/...`、`/tmp/v6orch`）。在 Mac 上换成 `$WORK` 及步骤 1 生成的文件，命令本身不变。

## 5. 待用户决定

1. **Δ 与锚点开会规则**：回放显示每个锚点都会开会，成本 ≈ 3600/Δ × 每次会话成本。计划在开发机上用脚本规划器做闭环对比（不调用模型）：Δ=60、Δ=300、"空闲持续两个锚点才开会"、"至少 k 台空闲才开会"，从同一状态各跑数小时，比较会话数/小时与空闲机器·秒。结果出来前，步骤 7 的登记不要固定 Δ。
2. **交期**：lot 映射方式实测 +10.7k，超出 8k 上限，未启用。可选：放宽上限；或改成与 ready 行对齐的单独一列（按值估算约 4–5k，未实测）。
3. **running_jobs 的步骤/完工字段**：约 +1.5 万，暂缓，按 A/B 和 smoke 的结果再定。
4. 步骤 5、6、8 的**模型预算**。
