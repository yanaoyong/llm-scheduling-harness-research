## 何时结束收集

1. 可开工但缺少已提交任务或有效显式等待的机组，从缺口首次出现时计时，连续等待达到 60 秒就停止模拟并请求计划。新计划版本、空提案、保存恢复都不能重置仍未解决的计时。
2. 机组后面没有已排任务时，先检查接续物料是否已有依据：当前就绪、前序正在执行，或前序在已确认计划中。只沿这些公开依据及已定任务顺序估算到达时间，不假设尚未选择的前序会自动开工。取机组预计可用和物料预计到达两者较晚的时刻，提前 15 秒形成提醒；没有支撑的远期候选仍保留在公共资料中。预测类决策距上次成功提交至少 60 秒，同轮纳入未来 60 秒的相关预测。真实等待、计划到期/失效仍可更早触发；只是新的预测变化不绕过合并间隔。
3. 只对上次确认批次之后新出现或实际约束有变化的需求计算容量，其相关完整资料达到输入预算的 85% 就提前收批。提交消耗已知目录的这一次容量通知，不把整个未排目录再次当作新到达。实际输入仍受完整 22 万/44 万预算检查；`release_time` 随观察时钟被钳制的变化不算新需求。
4. 计划即将到期时提前 15 秒请求续期；实际失效立即中断。已提交任务在收集过程中继续按原顺序执行，普通缺口不再每出现一个就打断。

没有需求、没有续期必要时，不在 60、120、180 秒整点制造决策。忙碌机组续排按公开均值预测，可能提前或滞后；这不是实际释放时刻保证。

`forecast_collection.py` 只沿已确认任务的机组顺序、前序关系、公开处理/占机/运输均值和换型表计算提醒依据；不运行启发式或优化器，不生成任务。公开导出增加 `readiness_basis`，区分正在执行的前序与尚未安排的路线。无法建立前序依据时保持未知；`conditional=true` 不会一律被排除。预测不认证未来批量、随机路线或动态物理可行性，真实执行仍由原校验器把关。

60 秒约束针对机组上**当前可执行、又没有现存任务队列或有效显式等待覆盖的缺口**，不承诺每个候选工序在 60 秒内开工。模型明确提交的等待也属于决定，其等待成本仍须纳入后续质量比较。模型若在期限到达后继续提交不能解决缺口的方案，模拟保持暂停，既有零进展限制会停止失败运行；程序不会自动补任务来掩盖失败。

## 一套系统、两种处理策略

- 初次：没有有效计划，或没有待执行任务、有效等待和正在执行的工作时，建立首段计划。保存状态已经有有效任务/在制工作时进入接续，不按程序是否刚启动判断。
- 初次同时到达的超量资料不能靠缩短时间窗口消除。每次观察冻结一个带 ID 的资料批次，按完整工序依赖单元装入；同批物料、前驱和机组绑定依赖不拆断。其余资料留在完整公共存储中，下一轮先装入尚未提供过的部分；不要求一次装下全厂后续工序。
- 接续：已有任务照原计划执行，新计划仍由模型明确保留、增加、取消或替换。任何提案检查、批次记录和容量计算都不生成任务或等待。模型缩短有效期到保留任务之前仍会被拒绝。
- 只在 `apply_candidate` 成功接受时写入批次回执；提案检查、被拒绝的提案、重复处理同一输出都不能提前消耗批次。回执和计划在同一事务中保存，恢复时一起还原。
- 批次回执区分已安排与未安排工序，不把“提供过资料”当作“需求已解决”。未安排需求、原始就绪等待起点和未展示溢出均继续保留。无需额外模型调用即可生成覆盖诊断。
- `apply_candidate` 可附带 `machine_reviews`：机组、planned/deferred/insufficient_information、理由和建议复查时刻。缺少说明记为 unreported；资料在包内、模型明确说明、已有生产安排分开保存。无效说明只记录错误，不取消合法计划。复查信息只是提醒元数据，不等于机组 hold，也不能延长真实可开工等待期限；实际预测时机仍遵守共用 60 秒合并间隔。
- 一批提交后，旧的超量目录不会让容量立即再次触发。剩余资料在下一次真实就绪期限、接续预测、计划到期/失效或新到达容量通知时继续处理。若就绪期限已到，可能在同一模拟时刻处理多个**不同**的资料批次；全部资料提供后仍无生产进展，则连续 3 次零进展失败停止，变更计划/批次 ID 不能绕过。
- 模型决策时模拟时钟暂停；两次决策之间正常执行任务。不使用后台模型或并行修改计划。

## 有限窗口下如何组织资料

- 完整公开问题、原计划、执行状态、需求台账、历史与工具结果保存在副本内的公共资料存储。模型可通过公共引用精确查询。
- 当前输入围绕冻结批次组织。接续时依次优先：真实就绪缺口及其期限、本次触发机组、临近且有依据的接续预测、其他尚未展示资料，然后按首次观察时间和源顺序填充。旧资料只要仍相关就可以重新装入，不会因存在几条新记录就被整批排除。初次超量需求仍按尚未提供的完整资料单元分批。这个顺序只组织资料，不决定生产任务。
- `focus_coverage` 列出本次重点机组及实际包内候选数，分别显示完整、部分和未装入；机组候选可能重叠，不能相加当作订单数。重点资料的前驱/同物料/机组绑定依赖一起装入。超量资料保留完整公共引用，不能把未装入的重点机组当作已处理。
- 默认同时展示相关机组和原计划记录。超过预算时保留明确的总数、遗漏数和公共引用，支持分页；不要求全厂机组、全部工序、完整计划必须同时进入窗口。
- 单个资料单元本身超限时，返回明确的分页读取状态。完整内容仍可获取，不静默截断，不把未展示内容当作不存在。
- 取消该实验路径原有的 48 工序、8 条历史、60k 结果预览等固定上限，改由 token 预算控制。保留 400 万字符的应急错误检查；正常输入容量不按字符数决定。
- 生产编译和提交仍对完整权威快照及全厂责任范围进行校验；显示的资源子集不会缩小计划责任。副本的实验入口不再把机组数量写死为 913。
- 所有生产任务及显式等待均须通过提案和选择流程提交。资料组织、覆盖诊断和触发计算均不自动选择任务、不调用模型。

“无损”指原始公共资料可精确恢复、展示记录字段不变；不意味着有限上下文必须同时包含全部资料。已有导出器的 `lookahead_depth=2` 和公开预测范围两组相同，没有把隐藏未来加入输入。

独立审计重新计算缺口、计时和等待成本，仍检查已排任务漏执行及物理前缀；测试不伪造终态。容量数值和公开预测因果性由另外的资料与扰动测试验证，审计报告不会声称仅靠事件审计已经重新证明这些数值。旧默认审计不接受新等待规则，防止不同实验语义混用。

本地计数使用固定哈希的 `o200k_base`。最新 v3 pilot 的 G2 首请求服务端报告 369,895 输入 tokens（修改前历史 pilot 为 393,402），实际超过 272,000；这不证明已验证整个 544,000 上限，也不证明本地 tokenizer 与服务端逐 token 完全一致。10,000 tokens 包装空间仍是预留。

## 后续实际实验的比较口径

两组使用配对初始状态、相同外部负载和共同评估终点。主指标是处理相同需求工作量的全部模型调用数，包含查询、提案、确认、修正和失败调用。同步比较已解决/未解决需求、重复处理、延期、产出、机组等待、计划失效和零进展失败；不能只看决策批次数或通过积压任务减少表面调用。

动态周期和容量分包数只作为机制指标。两组都未触及容量时，应报告该负载没有识别出窗口收益。默认配置仍禁用模型；已登记的本轮 pilot 均已停止、封存，不自动重试或继续运行。
