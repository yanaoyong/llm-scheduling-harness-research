| 一个会话跨所有周期一直恢复 | 不要。历史会越积越长，压缩过程对我们是黑盒，旧状态还可能和模拟器的真实状态不一致，实验也很难复现和审计 |

具体怎么做：
1. **每个周期启动一次 `codex exec`。** 我们自己写一个 MCP 服务，暴露这些工具：
   - `get_decision_snapshot`：取当前决策需要的完整状态
   - `query_candidates`、`read_detail`：只读查询，可以一次并行多个
   - `validate_plan`：就是只校验不提交的 `dry_run`
   - `submit_plan`：唯一的写操作，原子提交

   提交成功，或者用完本轮的工具调用和时间预算，会话就结束。
2. **周期之间的衔接靠快照，不靠会话历史。** 快照里有：状态版本、当前计划、执行状态、全局工序账本、等待原因、上一轮回执和规范化结果，以及模型自己写的简短跨轮笔记（现有的 `machine_reviews` / `fact_memory` 可以复用）。模拟器的状态始终是唯一的权威来源。
3. **快照按变化频率排序。** 规则、工具定义、工艺资料这些不变的内容放在前面，当前状态放在后面，这样会话内的多次请求可以命中提示缓存，重发上下文的 token 成本会明显下降。
4. **审计从"每次调用一个动作"改成"每次工具调用都留记录"。**
   - MCP 服务给每次工具调用记下状态版本、参数和结果摘要。
   - `codex --json` 会输出每个回合的用量事件，我们分开统计：周期数、会话内的模型请求数、工具调用次数、token（含缓存命中）、失败次数。
5. **必须说清楚的一点：** 一个会话内部仍然会有多次模型请求，每次工具往返算一次。所以"每周期一个会话"本身主要省的是 token 和进程开销。真正减少请求次数，靠的是周期化（轮数变少）、原子提交（省掉确认）和完整快照（少查资料）。这四样要一起做，指标上也分开报告，避免把进程数变少当成请求数变少。

还有一个风险：这样改，审计要从现有的严格逐调用台账迁移到 MCP 工具层。我建议保留现有台账里的哈希和证据链思路，只改变记录的粒度。
