## 一、提交格式里的冗余

模型每次提交一份 delta（对上一版计划的增删改）。里面有 4 处是程序本来就知道、或者同一信息写了两遍：

| 冗余 | 现状 | 问题 |

| 1. 任务身份写四遍 | 每个任务同时写 `operation_ids`、`lot_ids`、`steps`、`visits`，而工序 ID 本身就是"批次:工步:访问次数" | 模型多写约 35% 的字；只要四者对不上，就因 `task_identity` 被拒 |
| 2. 要回抄 4 个哈希 | delta 里的 `anchors` 要求模型原样抄回基础计划、观测、状态、数据源的 4 个 SHA256 | 每个 64 位十六进制，共约 150–200 token；抄错一位就因 `stale_anchor` 被拒。提交时已经有 `expected_state_version` 检查版本，这是从 v5 "提议+确认"时代留下的 |
| 3. 取消列表写两遍 | `keep: {mode: 'all_pending_except', ids: [...]}` 和 `cancel_ids: [...]` 要写同一份列表，hold 也一样 | 两份不一致就会被拒 |
| 4. 固定字段 | `schema`、`order_policy` 是常量；`plan_header` 里的 `created_at`（就是当前时间）、`scope` 程序都能填 | 白写，写错还会被拒 |

- 主要不是 token。输出 token 单价比输入贵，但任务数通常只有几十到一两百个，省下的绝对量不大。
- 关键在出错率。这些字段每一个都是"模型可能写错、写错就被拒"的点。被拒就要重新提交，多一轮请求。而请求次数正是我们的主指标之一，所以这些冗余会直接推高调用次数。

**什么是"即将可开工"**
